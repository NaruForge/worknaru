# 0002. Daemon 중심 코어와 웹·데스크톱 공통 접속 구조 채택

- 날짜: 2026-09-08
- Status: Accepted
- 관련 Work Item: [#3 WorkNaru 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 관련 ADR: [0001. 외부 AI 에이전트 연결에 ACP 채택](0001-use-acp-for-agent-connections.md)
- 관련 문서: [제품 방향](../../README.md), [프로젝트 기록 규약](../project-records.md)

## Context

WorkNaru는 플랫폼과 독립적인 업무 Module로 구성되는 AI Workspace다. 외부 AI 에이전트 연결에는 ADR-0001에서 ACP를 채택했다. 이번에는 이 연결과 실행·세션 관리를 담당할 코어의 배치, 사용자 화면의 접속 방식, 실행 수명을 결정한다.

사용자는 앱을 종료하면 AI 실행도 종료되는 예측 가능한 동작을 원하면서, 웹 브라우저와 데스크톱 앱이 같은 Daemon에 접속하는 Paseo의 구조를 참고하고자 했다. 독립 실행 가능한 코어와 앱이 관리하는 실행 수명은 함께 지원할 수 있으므로, 접속 구조와 Daemon을 누가 시작·종료하는지를 구분한다.

Paseo의 공식 문서에서 확인한 참고 구조는 다음과 같다. 이 자료는 문서 검토의 근거이며 WorkNaru 구현 검증 결과는 아니다.

- Daemon이 외부 에이전트 CLI를 실행·관리하고 클라이언트에 기능을 제공한다. [Paseo Providers](https://paseo.sh/docs/providers.md)
- Daemon은 API 및 WebSocket과 같은 주소에서 웹 UI도 제공할 수 있다. 웹 UI를 Daemon 패키지에 포함해 버전을 맞추는 방식이다. [Paseo 웹 UI](https://paseo.sh/docs/web-ui.md)
- 클라이언트에서 Daemon으로 접속하는 통신과 Daemon에서 에이전트를 관리하는 연결은 서로 다른 경계다. [Paseo Connectivity](https://paseo.sh/docs/connectivity.md)

검토한 대안은 다음과 같다.

| 대안 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 앱의 기존 백엔드에 실행 관리 포함 | 초기 프로세스 구성이 단순하고 앱 수명을 따르기 쉽다. | 웹·데스크톱이 공유하는 독립 코어로 확장하려면 실행 관리와 앱의 결합을 풀어야 한다. |
| 앱 전용 내부 실행 프로세스 | UI와 실행 관리의 책임을 나누면서 앱이 시작·종료를 관리할 수 있다. | 앱 없이 실행하거나 다른 클라이언트가 공통 규약으로 접속하는 구조는 별도로 마련해야 한다. |
| 독립 실행 가능한 Daemon과 웹·데스크톱 클라이언트 | 같은 실행 코어와 상태를 두 클라이언트가 공유하고, 앱 관리 실행과 독립 실행을 함께 지원할 수 있다. | API·이벤트, 여러 클라이언트의 상태 일관성, 실행 소유권과 종료 정책을 설계해야 한다. 목표 접속 경험에 적합해 채택한다. |

## Decision

**Paseo의 접속·실행 구조를 참고해, 독립 실행 가능한 WorkNaru Daemon을 공통 코어로 두고 웹 브라우저와 데스크톱 앱이 같은 Daemon에 접속하도록 한다.**

### 구성요소와 책임

- **Daemon:** UI와 별도 프로세스로 실행한다. ACP 연결, 에이전트 실행·종료와 생성(spawn), 세션 및 실행 상태 관리를 담당한다. WorkNaru가 관리하는 공유 상태의 원본을 소유하고 클라이언트에 전달한다. 프로바이더 고유 대화 저장·복구의 책임은 ADR-0001의 경계를 따른다.
- **Web UI:** 브라우저에서 Daemon에 접속해 작업을 요청하고 상태와 기록을 표시한다.
- **데스크톱 앱:** 공통 Web UI와 접속 규약을 사용한다. 로컬 Daemon을 시작·종료하는 역할과 기존 Daemon에 접속하는 역할을 구분한다.
- **공통 접속 계약:** 웹과 데스크톱이 같은 API·이벤트 계약을 사용한다. 이 계약은 Daemon과 외부 에이전트 사이의 ACP 연결과 별개다.

코어의 독립성은 항상 상주하거나 운영체제 서비스로 등록해야 한다는 뜻이 아니다. 처음에는 로컬 Daemon 하나에 웹과 데스크톱이 접속하는 범위에 집중한다. 플랫폼과 Module의 업무 책임 구분은 README를 따른다.

### 실행 방식별 종료 정책

| 실행 방식 | Daemon의 수명 관리 | 클라이언트 종료 시 동작 |
| --- | --- | --- |
| 데스크톱 앱이 시작한 전용 Daemon | 해당 데스크톱 앱 | 앱을 명시적으로 종료하면 작업과 관리 대상 에이전트를 정리하고 Daemon도 종료한다. 여기에 접속한 브라우저 연결도 종료된다. |
| 사용자가 별도로 시작한 Daemon | 독립 실행을 관리하는 사용자 | 데스크톱 앱이나 브라우저를 닫아도 접속만 해제한다. Daemon과 실행은 유지하며 별도의 명시적 종료로 정리한다. |

브라우저 탭 닫기, UI 새로고침과 일시적 연결 끊김을 Daemon 종료 요청으로 취급하지 않는다. 기존 Daemon에 접속했다는 이유만으로 클라이언트가 그 Daemon의 수명을 소유하지 않는다.

앱 또는 Daemon의 종료는 대화·작업 기록 삭제를 의미하지 않는다. 기록을 보존하고 다음 접속에서 표시하며, 실제 실행의 재개 가능 범위는 프로바이더 기능과 후속 복구 설계에 따른다.

### 승인 근거

2026-09-08 설계 대화에서 사용자는 Paseo처럼 웹 브라우저와 데스크톱 앱이 같은 Daemon에 접속하는 구조를 제시했다. 이어 “접속 구조는 paseo의 구조를 차용한다고 보아도 될까요? 물론 paseo만큼 복잡한 기능을 넣을 필요는 없지만.”이라고 범위를 확인했다.

공통 Daemon, Web UI와 데스크톱 접속, 로컬 우선 범위 및 실행 방식별 종료 정책을 설명한 뒤 사용자가 “ADR로 기록합시다.”라고 요청했다. 이 합의를 근거로 `Accepted`로 기록한다.

### 이번 결정에서 확정하지 않는 사항

- Paseo 코드·패키지의 재사용이나 Paseo 기술 스택 채택
- 구현 언어, UI·데스크톱 프레임워크, API·이벤트 전송 기술과 배포 형식
- 데이터베이스와 이벤트 저장 형식, 재연결·복구 알고리즘
- 운영체제별 비정상 종료 정리 방식, 종료 제한 시간, 창 닫기·트레이 동작의 세부 UX
- 원격 중계, 다중 사용자, 여러 호스트 관리, 스케줄링과 운영체제 자동 시작 기능

## Consequences

### 장점

- 웹과 데스크톱에서 에이전트 실행과 세션 상태를 공유하고, 동일한 플랫폼 기능을 사용할 수 있다.
- 화면 구현과 공통 실행 코어의 책임을 분리해 UI 변경이 실행 관리에 미치는 영향을 줄인다.
- 앱과 함께 실행을 정리하는 기본 사용 방식과 독립적으로 Daemon을 운영하는 방식을 같은 코어로 수용한다.
- 원격 접속이나 장시간 실행이 필요해질 때 활용할 구조적 경계를 마련한다. 해당 기능의 구현 비용이 사라지는 것은 아니다.

### 비용과 위험

- 여러 클라이언트의 동시 요청, 취소와 승인 응답, 재연결 후 상태 전달을 일관되게 처리해야 한다. 프로세스를 나누는 것만으로 동기화가 해결되지는 않는다.
- Daemon의 시작 실패, 중복 실행, 클라이언트와의 버전 차이, 종료 도중 오류를 다뤄야 한다.
- 데스크톱 전용 Daemon에 브라우저가 접속한 경우에도 데스크톱 앱 종료가 실행 종료로 이어진다. 현재 실행 방식과 종료의 영향을 사용자에게 명확히 보여줘야 한다.
- 비정상 종료 시 관리 대상 에이전트가 방치되거나 기록이 손상되지 않도록 평상시 저장과 프로세스 정리 방법을 검증해야 한다. 정상 종료 시에만 기록을 저장하는 방식에 의존하지 않는다.
- Daemon 종료와 작업 취소는 이미 수행된 파일 변경이나 외부 작업을 자동으로 원복하지 않는다.
- 로컬 접속에도 클라이언트 접근 검증이 필요하다. 향후 원격 공개 시에는 인증·권한·통신 보안을 추가로 설계해야 한다. 프로세스 분리 자체를 보안 격리로 간주하지 않는다.

### 후속 설계에 미치는 영향

플랫폼 설계에서는 공통 API·이벤트 계약, 공유 상태와 저장 책임, 실행 소유권의 식별, 정상·비정상 종료와 재접속 동작을 구체화한다. 웹과 데스크톱의 동일 세션 조회, 동시 요청 처리, 두 실행 방식의 종료 정책을 검증 대상으로 삼는다.

이 ADR은 ADR-0001에서 미확정으로 남긴 플랫폼 코어의 배치와 접속 구조를 구체화하며 ACP 채택 결정을 대체하지 않는다. 작업 범위와 진행은 관련 GitHub Issue와 전용 Project에서 관리한다.
