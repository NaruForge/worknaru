# 0014. 공통 서비스 탐색과 Module 내부 탐색 분리

- 날짜: 2026-09-09
- Status: Accepted
- 관련 결정: [Module 정의](0006-define-modules-as-business-services.md), [Module 연결 계약](0009-use-a-common-module-platform-contract.md), [공통 Web UI](0002-use-daemon-core-with-web-and-desktop-clients.md)
- 상세 UI 기준: [공통 작업 화면과 첫 Chat](../design/workspace-chat-ui.md)

## Context

WorkNaru는 여러 업무 Module을 사용하는 Workspace이며, Chat은 첫 기본 제공 Module이다. 첫 화면의 탐색 방식이 이후 Module의 화면 구성에도 영향을 주므로 공통 탐색과 업무별 탐색의 관계를 정할 필요가 있다.

사용자는 첫 Chat UI가 서비스의 UI를 결정하는 중요한 분기점임을 강조했다. 같은 대화 내용을 사용한 네 시안을 비교했다.

| 시안 | 구조와 고려점 |
| --- | --- |
| A: 왼쪽 서비스 탐색과 Module 목록 분리 | 공통 탐색과 업무별 탐색의 위치가 명확하다. 두 탐색 영역이 본문 너비를 사용하므로 목록 접기와 좁은 창 대응이 필요하다. |
| B: 상단 서비스 전환 | 왼쪽을 Module 목록에 사용할 수 있다. 서비스가 늘 때 상단의 제한된 너비를 고려해야 한다. |
| C: 집중형 화면 | 본문을 넓게 사용하며 필요할 때 목록을 연다. 서비스와 작업의 발견 가능성을 별도로 보완해야 한다. |
| D: 작업 탭 | 여러 작업을 오가는 위치가 드러난다. 탭의 열기·닫기와 복원 등 추가 수명 관리가 필요하다. |

## Decision

**A안을 공통 작업 화면의 기준으로 삼는다. 플랫폼의 서비스 탐색과 Module 내부의 목록·본문을 분리한다.**

- 플랫폼은 현재 Workspace와 공통 서비스 탐색을 관리한다.
- Module은 자신의 작업 목록과 본문을 구성한다. Chat의 대화 목록을 다른 Module의 필수 구성으로 만들지 않는다.
- 목록이 필요 없는 Module은 해당 공간까지 본문에 사용한다.
- Module 목록은 독립적으로 접을 수 있다. 좁은 창에서는 필요할 때 여는 목록으로 전환하며 서비스 접근 경로를 유지한다.
- 화면 이동이나 목록 접기를 AI 실행 취소·Session 삭제로 취급하지 않는다. 실행 수명은 기존 플랫폼 계약을 따른다.

### 승인 근거와 범위

2026-09-09 사용자는 네 시안을 비교한 뒤 “확장성을 고려하면 A가 가장 좋아보여”라고 선택했다. 이어 탐색 너비·접기·좁은 창 배치와 Chat 실행·오류 상태의 구체화를 요청했다. 대화별 초안 유지, 키보드 조작과 상태별 안내를 포함한 A안 상세 시안을 제공한 뒤 사용자가 “승인합니다.”라고 명시했다.

승인 대상은 A안의 화면 구성과 상세 UI 동작이다. UI·데스크톱 프레임워크 선정, 보고서 Module 구현, 시안의 가상 응답·확인 결과를 실제 기능으로 채택하는 결정은 포함하지 않는다. 세부 치수와 상태별 표현은 연결된 설계 문서에서 다룬다.

## Consequences

- 다른 Module도 같은 서비스 탐색을 사용하면서 자신의 목록과 작업 화면을 구성할 수 있다.
- 서비스 탐색과 Module 탐색이 함께 보이는 화면은 본문 너비를 더 사용한다. 목록 접기와 창 크기별 배치를 함께 구현해야 한다.
- Module마다 목록 유무와 탐색 정보가 달라도 공통 화면이 열기·닫기와 포커스 이동을 처리해야 한다. 필요한 코드 경계는 첫 Chat 구현에서 확인한다.
- 보고서 배치 시안은 공간 활용을 확인한 예시다. 실제 업무 Module의 데이터·실행·저장 계약이나 전체 확장성을 검증한 근거로 간주하지 않는다.
- 외부 Module 설치, 전체 화면 구성요소 라이브러리와 범용 탭 관리 체계를 선제적으로 만들지 않는다.
