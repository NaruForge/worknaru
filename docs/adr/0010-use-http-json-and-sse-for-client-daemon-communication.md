# 0010. 클라이언트–Daemon 통신에 HTTP JSON과 SSE 사용

- 날짜: 2026-09-08
- Status: Rejected
- 관련 Work Item: [#3 WorkNaru 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 관련 ADR: [0002. 공통 Daemon 접속](0002-use-daemon-core-with-web-and-desktop-clients.md), [0005. TypeScript와 Node.js](0005-use-typescript-and-nodejs-for-daemon.md), [0009. Module 공통 계약](0009-use-a-common-module-platform-contract.md)
- 관련 설계: [화면과 Daemon의 통신 설계](../design/client-daemon-protocol.md)

### 검토 결과

2026-09-08 사용자가 Paseo와의 비교 및 단일 추천을 요청했다. 비교 후 “WebSocket으로 연결하고, Chat에 필요한 최소 명령과 알림부터 구현한다”는 추천에 사용자가 “승인합니다.”라고 응답했다. 이에 따라 이 HTTP JSON·SSE 전송 제안은 채택하지 않고, 선택한 방식을 [ADR-0011](0011-use-websocket-for-client-daemon-communication.md)에 기록한다. 이 제안은 승인된 적이 없으므로 `Superseded`가 아닌 `Rejected`로 기록한다.

아래 내용은 당시 제안의 근거로 보존한다. 연결된 통신 설계 문서는 이후 선택한 방식을 반영하며, 이 제안의 채택을 뜻하지 않는다.

## Context

웹·데스크톱이 공통 Daemon에 접속하고, Module이 같은 계약으로 Session·실행·승인·취소를 사용하는 구조를 정했다. 실제 전송 방식과 재접속 시 상태를 복원하는 방법은 아직 선택하지 않았다.

첫 Chat 검증에는 짧은 명령·조회, 점진적인 AI 출력, 도구·승인 상태, 화면을 다시 열었을 때의 현재 상태 복원이 필요하다. 화면 연결과 AI 실행의 수명은 분리해야 하며, 승인 응답이나 중지 버튼 때문에 항상 양방향 소켓이 필요한 것은 아니다.

| 대안 | 장점 | 비용과 판단 |
| --- | --- | --- |
| HTTP JSON + SSE | 명령별 HTTP 응답과 지속적인 서버 알림을 구분하고, 같은 HTTP 접근 계층을 사용할 수 있다. | 두 전송 경로의 도착 순서와 재접속을 다뤄야 한다. 현재 요구에 맞아 제안한다. |
| WebSocket으로 명령·이벤트 통합 | 한 연결로 양방향 메시지를 주고받고 다수 구독을 묶기 좋다. | 요청·응답 상관관계, 오류·버전·재접속 규약을 소켓 메시지에 마련해야 한다. 빈번한 양방향 스트리밍 요구가 생기면 재검토할 수 있다. |
| HTTP 조회 반복 | 초기 호출 구조가 단순하다. | 실시간 응답의 지연과 반복 조회 비용 사이에서 주기를 조정해야 하므로 기본 답변 전달에는 선택하지 않는다. |

SSE의 HTTP 이벤트 형식과 EventSource 인터페이스는 [WHATWG SSE 표준](https://html.spec.whatwg.org/multipage/server-sent-events.html), 양방향 소켓 API는 [WHATWG WebSockets 표준](https://websockets.spec.whatwg.org/), 명령 접수 응답의 의미는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)을 확인했다. 적합성 비교는 WorkNaru 요구에 따른 설계 판단이며 성능·배포 검증 결과가 아니다.

## Decision

다음 구성을 제안한다. 구체적인 연산·메시지 예시와 검증 기준은 [통신 설계](../design/client-daemon-protocol.md)에 둔다.

1. 클라이언트–Daemon의 조회·명령은 버전이 있는 HTTP JSON API, 실시간 상태는 SSE로 전달한다. Daemon–에이전트의 ACP 연결은 별도 경계로 유지한다.
2. 공통 플랫폼 클라이언트가 전송·런타임 검증·구독·재접속을 담당한다. SSE는 `fetch`로 읽고 HTTP 오류와 재접속을 명시적으로 처리한다. Module에는 업무에 필요한 플랫폼 기능과 상태를 제공한다.
3. 최초 접속과 재접속 모두 일관된 현재 상태 스냅샷을 먼저 보내고 이후 변경을 이어 보낸다. 첫 버전에는 과거 SSE 이벤트 커서 재생을 두지 않는다. 화면 복원에 필요한 누적 출력·기록은 Daemon에서 조회 가능해야 한다.
4. 명령에 요청 ID를 부여하고 같은 ID·같은 내용의 재전송을 중복 처리하지 않는다. 접수 기록은 자동 만료 없이 Daemon 재시작 뒤에도 유지하며, 접수 저장 뒤 외부 실행을 요청한다. 불명확한 외부 실행을 자동 재실행하지 않는다.
5. 승인 선택·취소 요청 접수·실제 실행 종료를 구분한다. 여러 화면의 동시 응답과 완료·취소 경쟁은 Daemon에서 원자적으로 판단한다. 공통 승인 구독은 현재 Workspace에서 Module 화면과 별도로 유지한다.

사용자의 “그럼 구체화 해줘” 요청을 근거로 작성한 설계 제안이다. 이 요청을 특정 전송 기술의 채택 승인으로 간주하지 않는다. 기존 ADR을 대체하지 않는다.

### 별도로 정해야 하는 사항

데이터베이스와 영속 기록·복구 구현, 전체 도메인 스키마와 대형 출력·이력 조회 API, 인증정보 발급과 Web UI·데스크톱 초기 접속, 라이브러리·프레임워크, 외부 Module·원격 접속 방식은 후속 설계 대상이다. 특히 저장·인증은 실제 사용 가능한 구현에 앞서 해결해야 하며 전송 기술만으로 충족되었다고 판단하지 않는다.

## Consequences

- Chat과 이후 Module이 같은 명령·실시간 상태 처리 기능을 사용할 수 있다. 화면 연결이 끊겨도 Daemon 상태를 기준으로 복원할 수 있는 계약이 생긴다.
- 첫 버전의 재접속은 이벤트 전체 재생보다 구현 범위가 작지만, 현재 상태 스냅샷과 후속 변경 사이에 틈이 없도록 처리해야 한다. 누적 기록 저장과 큰 결과의 제한·페이지 처리가 필요하다.
- HTTP 응답과 SSE 순서를 가정할 수 없으며, 요청 ID·리소스 ID로 결과를 맞춰야 한다. 접수 기록의 영속 보존과 클라이언트 임시 입력 보관에 비용이 든다.
- `fetch` 기반 SSE는 재시도와 형식 파싱을 직접 책임진다. 스트림 개수, 느린 클라이언트, 버퍼·프록시·절전의 영향을 구현에서 검증해야 한다.
- 화면 구독은 현재 상태 복원용이다. 모든 중간 이벤트를 반드시 처리해야 하는 업무 자동화나 정확히 한 번의 외부 부작용을 보장하는 통로가 아니다.
- 초기에 WebSocket을 도입하지 않아도 사용자 승인과 취소를 처리할 수 있다. 향후 음성·터미널 등 빈번한 양방향 데이터가 실제 요구가 되면 측정 근거와 함께 전송 방식 변경을 검토한다.
