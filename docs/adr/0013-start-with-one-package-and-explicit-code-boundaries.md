# 0013. 한 저장소·한 초기 패키지와 명시적 코드 경계로 시작

- 날짜: 2026-09-08
- Status: Accepted
- 관련 Work Item: [#5 저장소 구조와 코드 의존 규칙 설계](https://github.com/NaruForge/worknaru/issues/5)

- 근거: [제품 방향](../../README.md), [초기 개발 규칙](../../AGENTS.md), [저장소 구조 조사](../research/2026-09-08-repository-architecture.md)

## Context

제품 방향과 플랫폼·Module의 책임은 정의되어 있지만 제품 코드는 아직 없다. 다음 구현 후보는 메시지 접수·SQLite 저장·데몬 재시작 후 조회다. 사용자는 데몬 구현 전에 저장소 구조와 코드 의존 규칙을 설계하도록 요청했으며, 현재 초기 개발 규칙은 실제 기능에 필요한 구조만 만들도록 한다.

한 저장소에서 Daemon·공통 계약·client·앱·Module을 처음부터 여러 패키지로 나누면 공개 export와 의존성을 각각 관리할 수 있지만, 아직 소비자가 없는 코드에도 설치·빌드·연결 설정이 생긴다. 하나의 초기 패키지 안에서 소스 경계를 구분하면 첫 검증을 작게 시작할 수 있지만 import 경계가 자동으로 강제되지는 않는다. 별도 저장소 방식은 독립 권한·릴리스에 유리하나 현재 확인된 운영 요구에 비해 계약·버전 조정 비용이 크다.

사용자 검토에서 현재 단계의 상세 폴더 설계는 이르며 구조 검사도 아직 원하지 않는다는 의견을 받았다. 이 제안은 초기 패키지 관리 방식과 큰 책임 경계만 다룬다. 구체적인 폴더·파일 배치와 코드 연결 방법은 첫 기능을 구현하면서 정한다.

## Decision

다음 선택을 채택한다.

1. WorkNaru 코드를 현재 저장소에서 함께 관리하고 첫 Daemon 구현은 루트 패키지 하나로 시작한다. 미래 UI·데스크톱·Module을 위한 빈 workspace 패키지를 미리 만들지 않는다.
2. 기존 플랫폼·Module의 책임 경계를 유지한다. 이 역할 구분을 그대로 폴더나 패키지 목록으로 만들지 않는다.
3. 실제 빌드·런타임 의존성·배포 요구가 생기면 필요한 부분의 분리를 검토한다. 폴더·패키지·프로세스·배포 단위가 같아야 한다고 전제하지 않는다.

### 승인 근거와 범위

2026-09-08 상세 폴더 트리와 구조 검사 절차를 제거하고 큰 책임 경계와 첫 저장·재시작 조회 흐름으로 설계안을 줄였다. 사용자가 수정안을 검토한 뒤 “승인합니다. 커밋하고 작업을 시작하세요.”라고 요청했다. 이 승인을 근거로 위 선택을 Accepted로 기록한다.

승인 범위는 하나의 초기 패키지에서 시작하고, 세부 배치는 구현하면서 정하며 현재 구조 검사를 도입하지 않는 방향이다. 패키지 관리자·도구·프레임워크·Module 실행 방식까지 일괄 확정한 것은 아니다. 기존 Accepted ADR을 대체하지 않는다.

## Consequences

- 첫 저장·복원 흐름을 한 설치·검증 진입점에서 구현하면서 플랫폼과 Chat의 책임을 분리해 검토할 수 있다.
- 패키지 수준의 의존성 분리는 제공하지 않는다. 실제 UI 등이 추가될 때 실행 환경에 필요한 분리를 구체화해야 한다.
- 이후 패키지를 나누면 import 경로·manifest·빌드·테스트 설정을 옮기는 비용이 든다. 명시적인 책임 경계가 이 비용을 줄일 수 있지만 무비용 이전을 보장하지 않는다.
- 현재 구조 검사 도구·CI·별도 수동 점검 절차를 도입하지 않는다. 기능에 필요한 타입 검사와 동작 검증은 수행한다.
- 실제 업무 Module의 저장·서버 실행 계약과 외부 코드 격리는 여전히 후속 설계다. 같은 저장소나 공개 진입점이 보안 격리를 제공하는 것은 아니다.
