## Context

Module의 업무 책임과 플랫폼의 AI 실행 책임, Chat의 기본 제공 방식은 기존 결정에서 정했다. 실제 연결을 설계하려면 Module을 어떻게 인식하고 화면을 열며, AI 요청과 상태 전달을 어떤 공통 규칙으로 다룰지 정해야 한다.

Chat만을 기준으로 연결하면 보고서나 정형화 문서의 업무 데이터가 대화 구조에 종속될 수 있다. 반대로 첫 단계부터 모든 업무와 외부 Plugin 실행 방식을 일반화하면 검증 전 추측이 공통 기반에 늘어난다.

| 대안 | 장점 | 비용과 판단 |
| --- | --- | --- |
| Module마다 화면 등록과 Daemon 호출 코드를 따로 구성 | 첫 화면을 빠르게 연결할 수 있다. | 버전 호환, 요청 검증, 승인·취소와 재접속 처리가 분산되어 Module별로 달라질 수 있다. |
| 등록 정보와 플랫폼 기능 사용의 공통 계약을 둠 | 여러 Module이 같은 연결 규칙을 사용하면서 업무 데이터·흐름을 각자 소유할 수 있다. | 공통 계약의 범위와 변경 관리를 설계해야 한다. Chat과 다른 업무 사례로 작게 검증할 수 있어 채택한다. |
| 범용 Plugin 런타임과 업무 흐름 엔진을 먼저 구축 | 동적 설치와 다양한 실행 환경을 한 체계에서 다룰 수 있다. | 외부 코드 신뢰·격리·배포와 범용 데이터 모델까지 먼저 결정해야 한다. 초기 연결 검증에 비해 범위가 크다. |

## Decision

다음 구성을 채택한다. 계약의 연산과 사례는 [연결 규칙 설계](../design/module-platform-contract.md)에서 설명한다. 실제 API 이름·전송 형식과 후속으로 명시한 세부 사항은 구현 전 상세 설계에서 정한다.

1. Module은 식별자, 표시 이름, 계약 버전, 화면 진입점과 필요한 플랫폼 기능을 선언한다. 플랫폼이 중복·호환성과 기능 지원을 확인한다.
2. 플랫폼이 Module 화면에 검증된 작업 환경과 사용할 수 있는 기능을 제공하고, Module은 공통 계약으로 Session·실행·상태를 사용한다. 요청에 포함된 자체 선언을 권한 증명으로 취급하지 않는다.
3. 화면 수명과 AI 실행 수명을 구분한다. 화면 닫기는 구독 해제이며, 취소·승인·접속 복원은 Daemon의 상태를 기준으로 처리한다. 공통 승인 UI에서 사용자의 권한 응답을 받고 Module의 업무상 검토와 구분한다.
4. 같은 Session에는 한 번에 하나의 AI 실행을 허용하는 정책으로 시작한다. 실행 중 추가 요청은 명확히 거절하고, 자동 대기열이나 기존 실행의 자동 취소를 도입하지 않는다.
5. 첫 검증은 제품에 포함된 Chat의 명시적 등록과 기본 AI 흐름에 집중한다. 보고서·문서 정형화의 업무 참조와 결과 반영을 문서상으로 검토하고, 외부 코드 설치와 실행 격리는 후속 설계로 둔다.

AI 출력의 업무상 적용과 결과물 확정 규칙은 Module에 남긴다. 사용자 추가 Module이 도입되더라도 같은 연결 개념을 사용할 수 있게 하되, 코드 실행 방식이나 신뢰 수준까지 같다고 가정하지 않는다.

### 승인 근거

2026-09-08 사용자가 Module과 플랫폼의 연결 규칙에 대해 “초안을 작성해봐”라고 요청했다. 등록·화면 연결·AI 요청·상태와 결과 전달, Chat과 다른 업무 Module의 적용 사례를 작성하고 이 ADR과 함께 제시했다. 같은 Session에서 AI 실행을 하나씩 허용하는 초기 정책을 포함한 신규 제안임을 설명한 뒤, 사용자가 다음과 같이 승인했다.

> 승인합니다.

이 사용자 승인을 근거로 `Accepted`로 기록한다. 승인 범위는 연결 규칙 설계와 위의 초기 정책이다. 후속으로 남긴 기술·저장·접근·배포 설계까지 확정하거나 제품 구현을 승인한 것은 아니다. 기존 ADR은 대체하지 않는다.

## Consequences

- Chat과 이후 Module이 같은 실행·상태 규칙을 사용할 수 있으며, Module이 늘 때 기본 오류 처리를 반복 구현하는 부담을 줄일 수 있다.
- Session과 실행을 별도로 식별하고 요청 중복, 승인 경쟁과 재접속을 다루는 계약이 필요하다. 전송·저장 방식이 정해지기 전에는 이 동작이 구현되었다고 볼 수 없다.
- 같은 Session의 추가 요청을 거절하는 초기 정책은 순서를 단순하게 하지만, 실행 중 후속 입력이나 대기열이 필요한 사용자 경험은 추가 설계가 필요하다.
- 제공하는 기능 객체나 TypeScript 타입만으로 외부 Module 코드를 격리할 수는 없다. 신뢰할 수 없는 코드를 받으려면 실행 격리와 호출 권한 검증을 별도로 설계해야 한다.
- 보고서·문서 정형화 검토는 Chat에 종속된 공통 필드를 피하는 데 도움이 되지만, 해당 프로젝트의 코드 이식·실행·저장 호환성을 검증하지는 않는다.

Module 구현 언어, UI 프레임워크, 전송 기술, 저장·복구 방식, 외부 Module 설치·제거와 Workspace·Session 공유 정책은 별도의 후속 설계가 필요하다.
