## Context

Chat의 화면이 다시 연결되거나 Daemon이 재시작해도 접수된 요청, 부분 답변, 실행·승인 기록을 확인할 저장 기반이 필요하다. 요청 중복 판정과 실행 슬롯 확보, 최종 상태와 출력 저장이 각각 따로 성공하면 기록이 모순될 수 있으므로 관련 변경을 함께 커밋해야 한다.

현재 범위는 로컬 Daemon 하나와 여러 UI의 접속이며, Workspace는 폴더를 기준으로 한다. 폴더 기반이라는 결정만으로 대화 기록을 그 폴더 안에 저장하기로 정한 것은 아니다. 프로바이더 내부 대화와 Module 업무 데이터의 소유권은 기존 결정대로 구분한다.

| 대안 | 장점 | 비용·판단 |
| --- | --- | --- |
| JSON·JSONL 파일 | 읽기 쉽고 단순한 순차 기록을 시작하기 좋다. | 여러 기록의 원자성, 중복 요청 색인과 부분 쓰기·재구축 처리를 직접 설계해야 한다. |
| SQLite | 로컬 파일 기반이며 관련 기록을 트랜잭션과 제약으로 함께 관리할 수 있다. | 쓰기 직렬화, 마이그레이션, 백업과 저장 장애 처리가 필요하다. 초기 단일 Daemon 범위에 적합하다고 판단한다. |
| PostgreSQL 등 별도 DB 서버 | 여러 서버의 접근과 높은 동시 쓰기 요구에 대응할 여지가 있다. | 현재 로컬 범위에 서버 설치·운영 부담이 추가된다. 그 비용이 필요한 요구는 아직 확인되지 않았다. |
| Supabase | PostgreSQL과 인증·파일 저장 등 서버 기능을 함께 구성할 수 있다. | 현재 범위에는 계정·서버 운영이 추가된다. 팀 공유·클라우드 제품 요구가 생기면 재검토한다. |
| Turso Cloud + Turso Sync | 기기에서 로컬로 쓰고 클라우드와 변경을 주고받을 수 있다. | 동기화·충돌·실행 소유권 설계가 추가된다. 여러 독립 기기의 데이터 동기화가 필요할 때 검토한다. |

SQLite 공식 문서는 로컬 애플리케이션 저장과 애플리케이션 서버 뒤의 저장 용도를 설명하며, 한 DB에 동시 쓰기 하나라는 특성을 명시한다. WorkNaru 적합성은 이 제약과 현재 구조를 바탕으로 한 설계 판단이고, 부하 시험 결과는 아니다. [SQLite 사용 지침](https://www.sqlite.org/whentouse.html)

저장 위치도 비교했다. Workspace 안에 두면 폴더와 함께 옮기기 쉽지만 대화가 저장소 커밋·파일 동기화에 섞일 수 있고 폴더마다 저장 수명을 관리해야 한다. 사용자별 앱 데이터 영역에 두면 공통 접수·실행 기록을 한 Daemon이 관리하기 좋지만 폴더 복사만으로 대화가 이동하지 않는다.

사용자의 후속 요청에 따라 Paseo와 서비스 대안도 확인했다. 공개 커밋 `229f3cd5a8bfb5caacda457cc918bd910cad8da2`의 로컬 Daemon은 핵심 상태를 JSON 파일로 저장한다. SQLite는 Paseo의 저장 방식 차용이 아니라 WorkNaru의 관련 기록 일괄 저장 요구에 대한 제안이다. 파일 방식도 가능하며, Paseo의 안정성이 낮다는 비교 시험 결과는 없다. [Paseo 데이터 모델](https://github.com/getpaseo/paseo/blob/229f3cd5a8bfb5caacda457cc918bd910cad8da2/docs/data-model.md)

서비스 기능의 근거는 [Supabase DB](https://supabase.com/docs/guides/database/overview), [자체 운영](https://supabase.com/docs/guides/self-hosting), [Turso Sync](https://docs.turso.tech/sync/usage)를 참고한다. 현재 제품 적합성과 재검토 조건은 [설계 문서의 비교](../design/chat-storage-and-recovery.md)에 설명한다. 요금·성능 순위를 비교하거나 서비스 가입을 제안하는 결정은 아니다.

## Decision

**초기 로컬 플랫폼 기록의 데이터베이스로 SQLite를 채택한다.** 관련 기록을 트랜잭션과 제약으로 함께 관리하면서 별도 DB 서버 운영을 추가하지 않는다는 점을 선택 근거로 삼는다.

이를 적용하는 저장·복구 상세 설계안은 다음과 같다. SQLite 선택의 승인과 구체적인 저장 배치·운영값의 확정을 구분하며, 아래 항목의 세부 사항은 연결된 설계 문서에서 검토·구체화한다.

1. 공통 Session·Run·접수·출력·도구·승인 기록을 같은 DB에서 관리한다. 웹·데스크톱·Module 화면은 DB를 직접 수정하지 않는다.
2. 요청 접수와 상태·출력 변경은 관련 기록을 함께 커밋한 뒤 응답·알림으로 공개한다. 첫 설정안은 로컬 디스크의 WAL과 `synchronous=FULL`이며 실제 Windows 환경에서 검증한다. [WAL](https://www.sqlite.org/wal.html), [동기화 설정](https://www.sqlite.org/pragma.html#pragma_synchronous)
3. 사용자별 WorkNaru 데이터 영역에 DB 하나를 두고 Daemon 하나가 쓰기를 소유하며, 여러 Workspace를 식별자로 구분하는 구성을 제안한다. DB는 Workspace 폴더와 분리하고 폴더 삭제·이동과 앱 종료를 기록 삭제로 처리하지 않는다. 실제 저장 경로는 배포 설계에서 정한다.
4. 저장된 현재 상태와 출력으로 화면을 복원하며 네트워크 이벤트 전체를 보관하는 범용 이벤트 저장소는 첫 범위에 두지 않는다. 접수 장부는 첫 범위에서 자동 만료시키지 않는다.
5. 재시작 시 미확인 외부 실행을 자동 재전송하지 않고 저장 기록·프로세스·프로바이더 근거로 판별한다. 대화 열람, 다음 입력을 위한 맥락 복구, 중단된 Run 재개는 구분한다.

### 승인 근거와 범위

2026-09-08 사용자가 대화·AI 실행 기록의 저장과 복구 설계에 대해 “초안을 작성하고, 내게 쉽게 풀어 설명하세요.”라고 요청해 최초에는 Proposed로 작성했다. 이후 Paseo의 JSON 저장 방식, SQLite·PostgreSQL·Supabase·Turso 대안과 JSON 선택 시 관련 기록의 일괄 저장·중복 방지·장애 복구 부담을 비교했다. 사용자는 다음과 같이 결정했다.

> SQLite 선택을 승인합니다. 관련 사항을 처리하고 커밋, 푸쉬 하세요.

이 승인을 근거로 Accepted로 기록한다. 승인 대상은 초기 로컬 플랫폼 기록에 SQLite를 사용하는 선택과 관련 문서의 반영·커밋·푸시다. 구체적인 논리 모델·복구 사례·초기 한도·저장 위치와 배치는 연결된 설계 문서에서 구체화한다. 특정 Node.js DB 라이브러리, DB 암호화, 전체 Module 업무 저장 형식, 원격 동기화, 자동 백업·삭제 제품 기능이나 제품 코드 구현까지 확정한 것으로 취급하지 않는다.

## Consequences

- 접수 중복 방지와 상태 변경을 같은 저장 경계로 묶을 수 있고, 화면을 여러 개 열어도 공통 기록을 조회한다.
- 출력 커밋 후 표시하므로 쓰기 비용과 표시 지연이 생긴다. 짧은 출력 묶음과 제한된 버퍼를 검증해야 한다.
- DB에 저장하지 못한 수신 출력은 장애 시 잃을 수 있다. DB 커밋은 외부 에이전트·도구 실행의 정확히 한 번 수행을 보장하지 않는다.
- 데이터 영역에 DB와 WAL 등 부속 파일을 함께 관리해야 하며, 네트워크 파일시스템·실행 중 외부 동기화를 초기 운영 대상으로 삼지 않는다.
- 폴더만 복사하면 대화 기록이 따라가지 않는다. 내보내기·백업·복원과 사용자 데이터 보존 정책을 별도로 설계해야 한다.
- 로컬 DB에도 민감한 대화가 포함될 수 있어 접근 제한과 비밀정보 분리가 필요하다. 접수 장부의 장기 보존으로 저장량이 늘어나므로 명시적인 정리 정책이 후속으로 필요하다.
- SQLite 선택만으로 프로세스 소유권, ACP 맥락 복구, 인증·권한 검증이 해결되지는 않는다. 첫 구현 전에 관련 명세와 장애 검증을 완료해야 한다.
