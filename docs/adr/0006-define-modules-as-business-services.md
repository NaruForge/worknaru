# 0006. Module을 업무 서비스 단위로 정의하고 플랫폼과 책임 분리

- 날짜: 2026-09-08
- Status: Accepted
- 관련 Work Item: [#3 WorkNaru 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 관련 ADR: [0001. ACP 채택](0001-use-acp-for-agent-connections.md), [0002. Daemon과 클라이언트 구조](0002-use-daemon-core-with-web-and-desktop-clients.md), [0003. 폴더 기반 Workspace](0003-use-folder-based-workspaces.md)
- 관련 문서: [제품 정의와 책임 경계](../../README.md#플랫폼과-module), [프로젝트 기록 규약](../project-records.md)

## Context

기존 README는 Module을 독립적인 업무 기능으로 설명했으나 그 범위가 화면, AI 세션 또는 하나의 업무 서비스 중 어디까지인지 충분히 구체적이지 않았다. Session과 Module의 관계를 설계하기 전에 Module이 소유하는 업무 범위를 명확히 할 필요가 생겼다.

사용자는 `C:/Projects/lg-report-gen`의 보고서 생성 서비스와 `C:/Projects/DocCan`의 문서 정형화 서비스를 Module의 사례로 제시했다. 두 프로젝트의 README를 확인해 자료 입력, 편집·검토, 업무 데이터와 결과물까지 이어지는 흐름을 정의의 근거로 삼았다. DocCan의 AI 상호작용 단계는 사용자가 밝힌 향후 확장 방향이며 현재 구현으로 취급하지 않는다. 이 경로들은 논의 당시 참고한 로컬 프로젝트의 위치이며 WorkNaru의 실행 의존성이 아니다.

검토한 경계는 다음과 같다.

| 대안 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 화면 또는 AI 세션을 Module의 단위로 삼음 | Chat의 초기 흐름을 단순하게 표현할 수 있다. | 여러 화면과 수동·자동 처리가 이어지는 업무의 데이터·규칙을 어디서 소유할지 불명확해진다. 사용자가 제시한 서비스 범위를 담기에 부족하다. |
| 업무 서비스를 Module의 단위로 삼음 | 목적·입력·흐름·업무 데이터·결과를 하나의 책임 범위로 설명할 수 있다. | 공통 실행 기능과 업무별 규칙의 경계를 설계해야 한다. 서로 다른 업무 서비스를 수용하려는 제품 방향에 맞아 채택한다. |
| 독립 실행·배포되는 애플리케이션을 필수 단위로 삼음 | 배포와 실행의 경계가 명확하다. | 업무 개념을 정의하는 단계에서 프로세스와 패키징까지 제약한다. 현재 합의에는 이 제약을 요구할 근거가 없다. |

## Decision

**Module의 경계는 특정 업무 목적을 수행하는 서비스로 정하고, 공통 작업 환경과 실행 기반은 플랫폼의 책임으로 둔다.** 제품에서 사용하는 상세 정의, 다섯 가지 판별 항목과 업무 예시는 [README](../../README.md#플랫폼과-module)에 둔다. 이 ADR은 해당 경계를 선택한 근거와 영향을 기록한다.

Module이 업무 화면·규칙·데이터·처리 흐름과 결과를 소유하고, AI 사용 시 플랫폼이 제공하는 연결·실행 기능을 이용하도록 책임을 나눈다. 업무 내용의 검토·확정은 Module이 담당하고, 도구 실행 등의 권한 승인 처리는 플랫폼이 담당한다. 이는 ADR-0001의 AI 연결 책임과 ADR-0002의 공통 실행 구조를 구체화한다.

Module의 독립성은 업무 책임과 발전 가능성의 독립성을 뜻한다. 별도 프로세스·서버·데이터베이스·배포 패키지를 필수로 요구하지 않는다. 수동 처리와 AI 상호작용을 함께 포함할 수 있으며, 업무 데이터의 수명을 개별 AI 실행의 수명과 동일시하지 않는다.

### 승인 근거

2026-09-08 사용자가 Module을 위 두 프로젝트와 같은 서비스로 설명한 뒤, 업무 서비스 정의와 플랫폼 책임 경계를 논의했다. 이어 기록 위치를 질문했고, README에 정의·책임 경계·예시를 반영하고 ADR에 중요한 책임 분리의 근거와 제약을 남기는 제안에 다음과 같이 답했다.

> 동의합니다. 문서를 수정하세요.

이 합의를 근거로 `Accepted`로 기록한다. 제품 정의는 README에서 관리하고, 결정의 근거와 상태는 이 ADR에서 관리한다. 별도 용어집이나 정의의 복제본은 만들지 않는다.

### 이번 결정에서 확정하지 않는 사항

- Workspace·Module·업무 데이터·Session의 상세 관계, 세션 수와 Module 간 공유 방식
- Module의 등록·활성화·해제 API, 신뢰 모델과 외부 Plugin 설치 방식
- Module의 구현 언어, 프로세스 배치, 저장 위치와 스키마, 패키징·배포 방식
- 기존 두 프로젝트의 코드 재사용, 이식·연결 방식이나 통합 일정

## Consequences

- Chat뿐 아니라 보고서 작성과 문서 정형화처럼 여러 단계와 고유 데이터를 가진 서비스를 같은 제품 개념으로 설명할 수 있다.
- Module 설계에서 목적·입력·사용자 흐름·업무 데이터와 규칙·결과를 명시해 범위를 검토할 수 있다.
- 플랫폼이 업무별 편집·판정 규칙을 흡수하지 않도록 공통 기능을 실제 요구에 따라 추출해야 한다. 반대로 Module마다 에이전트 연결·실행 관리를 중복 구현하지 않도록 공통 계약이 필요하다.
- 업무 기록과 AI 실행 기록의 책임을 구분하고, 후속 설계에서 양쪽의 연결과 복구 동작을 정해야 한다. 이 정의만으로 세션 모델이나 저장 구현이 완성되지는 않는다.
- 기존 애플리케이션은 업무 범위의 참고 사례다. WorkNaru의 공통 기반에 연결하려면 기능과 책임을 따로 검토해야 하며, 현재 코드를 그대로 설치 가능한 Module로 간주하지 않는다.

이번 기록은 개념과 책임 경계의 결정이다. 플랫폼 설계 전체의 완료나 Module 구현·통합 승인을 의미하지 않는다.
