# Chat의 기록 저장과 복구 설계 초안

- 작성일: 2026-09-08
- 관련 Work Item: [#3 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 제품 개념: [README](../../README.md)
- 상위 계약: [Module과 플랫폼의 연결 규칙](module-platform-contract.md), [화면과 Daemon의 통신 설계](client-daemon-protocol.md)
- 저장 방식의 결정 근거와 승인 범위: [ADR-0012](../adr/0012-use-sqlite-for-local-platform-records.md)

이 문서는 Chat에 필요한 최소 기록, 저장 시점과 재시작 시 처리 규칙을 구체화한다. SQLite 선택의 승인 범위와 결정 상태는 ADR에서 관리한다. 아래 필드·복구 동작·저장 배치·운영값은 상세 설계 초안이며 SQLite 선택만으로 모두 확정되거나 구현·시험된 것은 아니다. 기존 플랫폼·Module 책임, ACP 연결, Daemon 종료 정책과 WebSocket 선택을 유지한다.

## 1. 사용자에게 보이는 동작

**WorkNaru가 요청을 받았다고 알리거나 답변을 보여주기 전에, 그 내용을 로컬 기록에 남긴다.** 다시 접속하면 이 기록으로 대화 화면을 복원한다.

예를 들어 “이 폴더의 문서를 요약해 줘”라고 요청한 뒤 앱이 갑자기 꺼졌다고 하자.

1. 다시 열면 접수된 질문과 저장된 답변까지 보인다.
2. AI가 계속 실행 중인지, 끝났는지, 중단됐는지 확인한다.
3. 끝났다는 근거가 있으면 완료로, 중단됐으면 그 사유와 함께 표시한다. 판단할 수 없으면 “작업 상태를 확인해야 합니다”라고 알린다.
4. 같은 요청을 자동으로 다시 실행하지 않는다. 사용자가 다시 시도하려면 기존 작업의 종료를 확인하고 새 요청으로 시작한다.

브라우저 새로고침은 화면만 다시 연결한다. 데스크톱이 시작한 전용 Daemon은 앱의 명시적 종료 시 작업도 정리하며, 독립 실행 Daemon은 접속한 앱을 닫아도 유지한다. 자세한 경계는 [ADR-0002](../adr/0002-use-daemon-core-with-web-and-desktop-clients.md)를 따른다.

기록 복원은 “어디까지 했는지 다시 볼 수 있다”는 뜻이다. 중단된 AI가 이어서 생각하거나 외부 파일 변경이 되돌아간다는 뜻은 아니다.

## 2. 저장소와 책임

첫 로컬 Daemon의 공통 기록은 **SQLite에 저장한다.** 상세 배치로는 사용자별 WorkNaru 데이터 영역에 DB 하나를 두고 여러 Workspace를 ID로 구분하며, 웹·데스크톱이 같은 Daemon을 통해 접근하는 방식을 제안한다. SQLite는 별도 데이터베이스 서버 없이 로컬 애플리케이션 기록을 관리하는 용도에 적합하다. 이를 현재 구조에 적용하는 것은 설계 판단이다. [SQLite 사용 지침](https://www.sqlite.org/whentouse.html)

데이터 영역은 Workspace 폴더와 분리한다. 따라서 작업 폴더를 Git에 올리거나 복사해도 대화가 자동으로 따라가지 않고, 폴더가 없어져도 기록을 즉시 지우지 않는다. 반대로 폴더만 백업해서는 대화 기록이 백업되지 않는다. 실제 OS 경로·설치별 구분은 배포 설계에서 정하며, 이번 문서 작업으로 데이터 폴더나 DB를 생성하지 않는다.

| 대상 | 원본과 저장 책임 |
| --- | --- |
| Workspace 등록, Session, Run, 접수·출력·승인 기록 | 플랫폼 Daemon이 SQLite에 저장한다. Chat이 실행 상태의 두 번째 원본을 만들지 않는다. |
| Chat의 대화 목록 표시·화면 설정 | Chat의 책임이다. 실행 상태와 분리하며 첫 저장 범위의 필수 항목은 아니다. |
| 작성 중이며 아직 보내지 않은 입력 | 화면의 초안이다. 서버 접수 기록과 구분하며 자동 보존은 이번 범위에서 보장하지 않는다. |
| 전송했으나 접수 확인을 못 받은 요청 | 공통 클라이언트가 복구용 임시 사본을 보관한다. 상세 규칙은 8절을 따른다. |
| 에이전트 내부 대화·추론 맥락과 고유 기록 | 프로바이더가 소유한다. 플랫폼에는 연결 식별자와 확인한 출력만 보관한다. |
| 보고서 본문·검토 상태 등 다른 Module 업무 데이터 | 해당 Module이 의미와 규칙을 소유한다. 이번 테이블을 범용 업무 데이터 모델로 확대하지 않는다. |

하나의 데이터 영역에는 쓰기를 소유하는 Daemon 하나만 허용한다. 앱이 별도로 시작되더라도 같은 데이터 영역을 두 Daemon이 동시에 관리하지 못하게 잠금과 소유권을 확인한다. SQLite 파일 잠금만으로 에이전트 실행 소유권까지 해결되지는 않는다. Windows의 구체적인 프로세스 잠금 방식은 구현 명세에서 정한다.

### Paseo의 실제 저장 방식과 대안 비교

2026-09-08 확인한 Paseo 공개 `main`의 커밋 `229f3cd5a8bfb5caacda457cc918bd910cad8da2`에서 **로컬 Daemon의 핵심 상태 저장은 JSON 파일 기반**이다. 데이터 모델 문서가 이를 명시하고, `AgentStorage`도 에이전트 기록을 JSON으로 저장한다. 쓰기는 기록별 큐와 임시 파일 작성 후 rename으로 관리한다. 따라서 이번 SQLite 제안은 Paseo의 DB 선택을 그대로 가져온 것이 아니다. [Paseo 데이터 모델](https://github.com/getpaseo/paseo/blob/229f3cd5a8bfb5caacda457cc918bd910cad8da2/docs/data-model.md), [AgentStorage 구현](https://github.com/getpaseo/paseo/blob/229f3cd5a8bfb5caacda457cc918bd910cad8da2/packages/server/src/server/agent/agent-storage.ts), [파일 쓰기 구현](https://github.com/getpaseo/paseo/blob/229f3cd5a8bfb5caacda457cc918bd910cad8da2/packages/server/src/server/atomic-file.ts)

같은 코드에서 화면 타임라인 저장 객체는 메모리 기반이다. 이 사실을 모든 프로바이더의 대화가 영속 저장되지 않는다는 뜻으로 확대하지 않는다. Paseo 자체 기록과 외부 에이전트 고유 저장은 별도다. 이 비교는 공개 코드 검토이며 사용자 PC에 설치된 버전·전체 서비스·장애 복구 성능을 시험한 결과는 아니다. [타임라인 구현](https://github.com/getpaseo/paseo/blob/229f3cd5a8bfb5caacda457cc918bd910cad8da2/packages/server/src/server/agent/agent-timeline-store.ts), [Paseo 프로바이더 설명](https://paseo.sh/docs/providers.md)

SQLite·PostgreSQL은 데이터베이스 엔진이며, Supabase·Turso Cloud는 저장 외 기능과 운영 방식도 제공하는 서비스다. 다음 평가는 “현재 WorkNaru의 단일 로컬 Daemon과 기록 복구”를 기준으로 한다.

| 선택지 | 강점 | 현재 WorkNaru에서의 비용·판단 | 더 유리해지는 조건 |
| --- | --- | --- | --- |
| Paseo처럼 JSON 파일 | 별도 DB 의존성 없이 파일을 읽고 관리하기 쉽다. | 여러 관련 기록의 일괄 저장·중복 제약·조회·형식 변경을 파일 저장 계층에서 구현해야 한다. 가능한 대안이지만 이번 복구 요구에는 추가 코드가 필요하다. | 저장할 정보가 소수의 독립 설정·메타데이터이고 복합 변경이 적을 때 |
| **SQLite** | 앱 내부에서 관계·제약·트랜잭션을 관리하며 저장용 서버가 필요 없다. | 한 번에 쓰기 하나라는 특성에 맞춰 짧게 커밋해야 한다. **현재 추천**이다. | 단일 로컬 Daemon이 기록을 소유할 때. [공식 지침](https://www.sqlite.org/whentouse.html) |
| PostgreSQL | 서버가 여러 접속과 동시 트랜잭션을 관리한다. | 로컬에서도 쓸 수 있으나 별도 DB 서버 설치·실행·업데이트가 추가된다. | 여러 Daemon·서버가 하나의 중앙 업무 저장소에 함께 쓰는 요구가 생길 때. [구조](https://www.postgresql.org/docs/current/tutorial-arch.html), [동시성](https://www.postgresql.org/docs/current/mvcc-intro.html) |
| Supabase | PostgreSQL에 인증·파일 저장 등 앱용 서비스를 함께 제공하고 호스팅·자체 운영을 선택할 수 있다. | 로컬 Chat의 장부만을 위해 도입하면 계정·서버 운영·접근 정책 범위가 커진다. 로컬 개발 구성도 별도로 운영한다. | 팀 계정, 서버상의 공동 데이터, 클라우드 제품이 주된 요구가 될 때. [DB](https://supabase.com/docs/guides/database/overview), [로컬 구성](https://supabase.com/docs/guides/local-development), [자체 운영](https://supabase.com/docs/guides/self-hosting) |
| Turso Cloud + Turso Sync | 로컬 읽기·쓰기와 클라우드 push/pull 동기화를 제공한다. | 동기화할 데이터와 충돌 규칙, 기기별 실행 소유권을 새로 정해야 한다. 기존 SQLite 파일을 단순 교체하는 것으로 취급하지 않는다. | 여러 기기가 각각 로컬 데이터를 소유하면서 오프라인 변경을 합쳐야 할 때. [동기화 사용법](https://docs.turso.tech/sync/usage) |

Turso 문서의 동기화 예시는 충돌 시 마지막 push가 이기는 규칙을 설명한다. 이를 Run 실행 슬롯·접수 장부·권한 승인에 그대로 적용하면 WorkNaru의 “한 번만 확정” 규칙을 대신할 수 없다. 미래 동기화를 도입해도 실행을 소유하는 Daemon과 공유할 업무 데이터는 별도로 설계해야 한다. 이는 해당 기능을 현재 요구에 적용한 판단이다. [Turso Sync 충돌 처리](https://docs.turso.tech/sync/usage)

웹·데스크톱·향후 휴대폰이 **같은 Daemon에 접속하는 것만으로 중앙 클라우드 DB가 필요해지는 것은 아니다.** 지금은 같은 Daemon이 상태를 공유하면 된다. 서로 다른 PC가 각자 작업하면서 같은 데이터를 합치거나 여러 사용자가 공동 편집해야 할 때 저장 구조를 다시 검토한다. SQLite가 모든 규모에서 우월하다는 결론이나 향후 DB 교체가 무비용이라는 약속은 하지 않는다.

## 3. 최소 데이터 구조

아래는 논리 모델이다. SQL DDL, 모든 필드의 자료형·색인·런타임 검증 코드는 구현 명세에서 작성한다. 시각은 표시와 진단에 사용하고, 변경 순서나 동시 실행 판정에는 ID·순번·제약을 사용한다.

| 기록 | 주요 정보 | 목적 |
| --- | --- | --- |
| 저장소 정보 | `storeEpoch`, `schemaVersion` | 접수 기록의 연속성과 DB 형식 버전을 구분한다. |
| Workspace | `workspaceId`, 등록한 폴더 참조, `revision` | 폴더와 기록을 연결한다. 경로 문자열을 ID로 사용하지 않는다. |
| Session | `sessionId`, `workspaceId`, 생성 Module, 에이전트 설정 참조, `activeRunId`, `revision`, 복구 가용성 | 여러 대화와 각 대화의 실행 가능 여부를 관리한다. 첫 Chat은 자신이 생성한 Session을 사용한다. |
| Run | `runId`, `sessionId`, 시작 요청 키, 실행 상태, 전달 단계, 소유 Daemon·프로세스 참조, 종료 근거·오류 | 사용자의 입력 한 번으로 시작한 AI 작업을 식별한다. |
| 접수 기록 | 호출 범위·`requestId`, 연산·대상·정규화 입력, 최초 접수 결과, 관련 리소스 ID | 응답을 잃어도 기존 요청을 확인하고 같은 일을 중복 접수하지 않는다. |
| 메시지·출력 블록 | `messageId`, `runId`, 역할·유형, Session 내 순번, `blockId`, 저장한 내용 조각·순번 | 질문, 누적 답변과 부분 출력을 표시한다. 완료 전 출력도 보존한다. |
| 도구·승인 기록 | `toolCallId`, `approvalId`, `runId`, 요청 내용·선택지, 확정 선택, 전달 상태, 유효 여부 | 무엇을 요청했고 사용자가 무엇을 선택했는지 확인한다. |
| 에이전트 연결 정보 | 플랫폼 Session과 프로바이더 Session의 대응, 기능 협상 결과, 프로세스 식별 근거 | 대화 불러오기 가능 여부와 남은 실행을 조사한다. |

Session의 Workspace 소속은 첫 범위에서 고정한다. Workspace 하나에 여러 Session을 둘 수 있지만 Module 간 Session 공유·이동·업무 데이터 연결의 저장 모델은 보류한다. 같은 폴더 판별과 폴더 이동·재연결의 상세 UX는 후속 접근 설계 대상이며, 경로가 바뀌었다고 기존 ID를 자동으로 다른 폴더에 붙이지 않는다.

필수 불변 조건은 다음과 같다.

- 모든 Session·Run·출력·승인은 유효한 상위 기록을 참조하며 Workspace 소속이 일치한다. SQLite 연결마다 외래 키 검사를 활성화한다.
- 접수 키는 `(인증 주체, 서버가 인정한 Module 호출 범위, workspaceId, requestId)`의 유일 값이다. 같은 키의 다른 내용은 충돌이다. 인증 주체·범위는 본문 주장을 그대로 신뢰하지 않는다.
- `activeRunId` 확보와 Run 생성은 같은 트랜잭션에서 처리한다. Session별 미종료 Run 유일성도 DB 제약으로 보강한다. 복구 차단 중에는 슬롯이 비어 있어도 실행을 거절한다.
- Run 상태는 기존의 `running`, `waiting_for_approval`, `cancelling`, `completed`, `failed`, `cancelled`를 유지한다. 접수 직후의 `running`은 작업 관리가 시작됐다는 뜻이며, 에이전트 전달 완료는 별도 정보다.
- `completed`, `failed`, `cancelled` 중 하나로 확정하면 늦은 이벤트로 되돌리지 않는다. 최종 상태가 불명확한 동안에는 별도 복구 가용성으로 새 실행을 막는다.

## 4. 언제 저장하는가

**사용자에게 접수·변경을 확정해서 알리는 기준은 트랜잭션 커밋 성공이다.** 트랜잭션은 관련 기록을 전부 함께 저장하거나 전부 취소하는 단위다. 외부 에이전트 호출은 DB 트랜잭션 안에서 기다리지 않는다.

| 시점 | 한 트랜잭션으로 저장할 내용 | 저장 이후 동작 |
| --- | --- | --- |
| Session 생성 접수 | Session과 접수 결과, Workspace revision | 플랫폼 Session ID를 응답한다. 프로바이더 Session 준비는 별도 가용성으로 표시한다. |
| 실행 접수 | 중복 키 확인, 실행 슬롯 확보, Run, 사용자 메시지, 접수 결과, 관련 revision | 접수 응답·알림 후 외부 전달 절차를 진행한다. 응답과 알림의 도착 순서는 가정하지 않는다. |
| 답변·도구 진행 수신 | 새 출력 조각·도구 변경과 관련 revision | 저장된 부분을 화면에 보낸다. |
| 승인 요청 수신 | 승인 내용·선택지·유효 상태, Run 대기 상태, 관련 revision | 공통 승인 UI에 알린다. |
| 사용자 승인 응답 | 첫 유효 선택 확정, 응답 접수 기록, 전달 대기 정보, 관련 revision | 선택을 에이전트에 전달한다. 선택 확정과 실제 전달을 구분한다. |
| 취소 접수 | 접수 기록, `cancelling`, 미처리 승인 종료, 관련 revision | 에이전트에 취소를 요청한다. |
| 최종 결과 확인 | 남은 출력, 최종 상태·근거, 미처리 승인 정리, 슬롯 해제, 관련 revision | 완료·실패·취소를 화면에 알린다. |

텍스트는 짧은 묶음으로 저장해 쓰기 횟수를 줄인다. 최초 제안은 최대 100ms 또는 UTF-8 32KiB 중 먼저 도달한 시점에 커밋하며, 승인 요청·종료 등 상태 경계에서는 앞선 출력을 먼저 반영한다. 이는 조정할 초기값이며 지연·성능 보장이 아니다. 대기 메모리에도 한도를 두고 무한히 쌓지 않는다.

화면은 사용자가 보낸 질문을 먼저 표시할 수 있으나 커밋 확인 전에는 “보내는 중”으로 구분한다. AI의 미저장 출력을 저장된 답변처럼 노출하지 않는다. 비정상 종료로 아직 저장하지 않은 수신 조각은 잃을 수 있으므로 “AI가 생성한 모든 글자를 보존한다”는 보장은 하지 않는다.

SQLite는 로컬 디스크에서 WAL과 `synchronous=FULL`을 사용하는 안으로 시작한다. WAL 모드는 추가 파일·체크포인트 관리가 필요하며 네트워크 파일시스템에는 두지 않는다. FULL은 커밋마다 WAL 동기화를 추가한다. 실제 저장장치·드라이버의 동작까지 무조건 보장하는 것으로 표현하지 않는다. [WAL 문서](https://www.sqlite.org/wal.html), [동기화 설정](https://www.sqlite.org/pragma.html#pragma_synchronous)

저장 실패 시 새 변경 명령을 차단하고 저장 장애를 알린다. 이미 진행 중인 에이전트에는 가능한 취소·정리를 요청하되, 그 결과를 저장하지 못했으면 성공·취소 완료로 확정하지 않는다. 마지막 저장 상태와 현재 저장 장애를 구분해서 보여주고, 정상화 후 프로세스 상태를 조사한다. 원본 DB 대신 임시 빈 DB로 계속 실행하지 않는다.

## 5. 접수와 실제 AI 전달 사이의 장애

DB 저장과 외부 에이전트 호출을 하나의 트랜잭션으로 묶을 수 없으므로, Run에 내부 전달 단계 `not_attempted`, `attempting`, `acknowledged`를 기록한다. 이는 새 Run 상태가 아니다. `acknowledged`는 해당 어댑터가 식별 가능한 수신 근거를 제공할 때만 기록하며, 단순 소켓 쓰기 성공을 AI 접수 확인으로 취급하지 않는다.

1. 요청과 Run을 `not_attempted`로 커밋한다.
2. 현재 소유 Daemon만 조건부 갱신으로 `attempting`을 커밋한 후 에이전트에 한 번 전달한다.
3. 확인한 수신·출력·종료 근거를 저장한다. 전달 기록 갱신 전에 죽을 수 있으므로 `attempting`은 “전달됐을 수도 있음”으로 해석한다.

UI의 같은 요청 재전송은 최초 접수 결과를 반환할 뿐 이 전달 절차를 다시 시작하지 않는다. 재시작 때도 미처리 접수 기록을 자동으로 에이전트에 보내는 대기열을 두지 않는다.

| 장애 당시 기록 | 재시작 시 판단 |
| --- | --- |
| 접수 커밋 전 | 정상적인 같은 저장소에서 기록 없음이 확인되면 통신 계약대로 같은 요청을 재전송할 수 있다. |
| `not_attempted` | 이전 소유자가 종료됐음을 확인하면 전달 전 중단으로 `failed` 처리한다. 사용자는 별도의 새 요청으로 다시 시도할 수 있다. |
| `attempting` 또는 수신 근거만 있음 | 실제 실행과 종료 결과를 조사한다. 전달되지 않았다고 추정하거나 자동 재전송하지 않는다. |
| 최종 결과 커밋 후 알림 전 | 저장된 최종 결과를 화면에 복원한다. 다시 실행하지 않는다. |

승인 선택도 확정 기록과 에이전트 전달을 구분한다. 재시작 후 옛 ACP 요청 번호로 응답을 재전송하지 않는다. 유효한 같은 승인 요청을 식별하고 안전한 전달을 확인할 수 있을 때만 처리하며, 불가능하면 실행 복구·정리 절차로 넘긴다. 외부 파일 변경이나 외부 서비스 호출의 “정확히 한 번 실행”은 이 접수 기록이 보장하지 않는다.

## 6. 재접속과 Daemon 재시작

### 화면 연결만 끊긴 경우

Daemon은 실행과 저장을 계속한다. 화면은 다시 인증하고 구독을 요청해 현재 상태 스냅샷과 그 이후 변경 알림을 순서대로 받는다. 입력을 자동 재실행하지 않으며 결과가 불명확한 요청은 먼저 접수 기록을 조회한다.

첫 구현은 Daemon의 공통 상태 처리 큐에서 쓰기 커밋과 스냅샷 구독 등록을 순서대로 수행하는 안을 제안한다. 읽기 트랜잭션으로 상태·revision을 확보하고 이후 변경 수신을 등록하는 사이에 다른 쓰기가 끼어들지 못하게 한다. 확보한 버전의 스냅샷을 먼저 보내고 뒤이은 변경을 보낸다. 네트워크 전송을 기다리며 DB 트랜잭션을 잡아두지 않는다.

출력 변경은 Session revision을, 목록·공통 승인을 바꾸는 변경은 Workspace revision도 같은 트랜잭션에서 올린다. DB 상태는 저장 직후 바뀌었지만 알림을 보내기 전에 프로세스가 종료돼도, 새 연결은 DB에서 복원한다. 네트워크 이벤트 전체를 영속 보관·재생하는 이벤트 저장소는 첫 범위에 두지 않는다.

### Daemon 자체가 재시작한 경우

1. 데이터 영역의 단일 소유권을 확보하고 DB 복구·버전·무결성을 확인한다. 실패하면 실행을 열지 않는다.
2. 새 `daemonInstanceId`를 발급한다. 정상적인 같은 저장소의 재시작은 `storeEpoch`를 유지한다.
3. 미종료 Run이 있는 Session을 “복구 확인 중”으로 차단하고 기록 조회는 제공한다. 저장된 `running`만 보고 실제로 실행 중이라고 표시하지 않는다.
4. 이전 Daemon·에이전트의 실행 여부와 프로바이더 기록을 확인하고 아래 기준으로 정리한다.
5. 확인 결과·승인 정리·최종 상태를 저장한 뒤 실행 가능 여부와 화면을 갱신한다.

| 확인 결과 | 처리 |
| --- | --- |
| 최종 결과가 이미 DB에 저장됨 | 그대로 표시한다. 프로바이더 연결 복구는 다음 입력을 받을 준비와 별개다. |
| 프로바이더에서 해당 Run의 종료를 명확히 확인 | 대응이 검증된 결과만 보충하고 최종 상태를 확정한다. 대화 끝에 답변이 있다는 사실만으로 해당 Run 완료를 추측하지 않는다. |
| 관리하던 에이전트가 남아 있음 | 첫 범위에서는 진행 작업에 자동 재부착하지 않고, 소유권이 확인된 프로세스를 취소·정리한 뒤 결과를 판별한다. |
| 실행이 끝났거나 정리됐지만 결과 확인 불가 | `failed`와 `EXECUTION_OUTCOME_UNKNOWN`을 기록한다. 파일 변경이 없었다는 뜻은 아니다. |
| 남은 프로세스의 소유권·종료 여부도 확인 불가 | 해당 Session의 새 실행을 계속 막고 수동 확인을 안내한다. 시간 경과만으로 슬롯을 해제하지 않는다. |

프로세스 ID는 재사용될 수 있으므로 PID만으로 종료 대상을 정하지 않는다. 시작 시각·소유 Daemon·관리 프로세스 그룹 등으로 소유권을 검증해야 한다. Windows 프로세스 트리 정리 수단과 조사·종료 시간 한도는 첫 실행 구현 전에 확정·검증할 항목이다. 정상 종료도 신규 접수를 막고 진행 작업 정리와 마지막 기록 저장을 시도하며, 기한 내 확인하지 못한 작업을 성공으로 기록하지 않는다.

프로바이더가 이전 대화 불러오기를 지원하고 실제 복구에 성공하면 다음 사용자 입력을 같은 대화에서 받을 수 있다. 미지원·실패 시 저장된 대화는 열람 가능하게 두고 새 대화 시작을 안내한다. 저장된 전문을 자동으로 새 에이전트에 보내 기존 맥락과 같다고 취급하지 않는다. ACP의 `session/load`와 `session/resume`은 협상한 지원 기능을 확인해야 하며, 실제 어댑터 지원과 진행 Run 재개는 별도 검증 대상이다. [ACP Session Setup](https://agentclientprotocol.com/protocol/v1/session-setup)

프로바이더의 대화 재생은 일반 실시간 출력과 구분해 받는다. 안정적인 대응 ID·순번으로 검증할 수 있는 내용만 기존 기록과 조정하며, 식별이 불가능한 전문을 기존 메시지 뒤에 무조건 덧붙이지 않는다. 최초 Chat 검증에서는 프로바이더 대화 가져오기 전체 기능을 구현하지 않고, 연결 복구와 중복 없는 화면 복원을 확인한다.

## 7. 긴 대화와 출력

질문·답변의 본문과 도구 표시 내용을 처음에는 같은 DB 안에 저장한다. 외부 파일을 동시에 커밋해야 하는 구조를 피하고, 긴 텍스트는 불변 조각으로 나누어 순서대로 읽는다. 이미지·첨부 파일·범용 결과물 저장은 이번 첫 텍스트 범위에서 제외한다.

스냅샷은 최근 메시지 요약과 현재 Run의 상태·승인을 담으며 본문에는 바이트 한도를 둔다. 큰 본문은 `sessionId`, `messageId`, `blockId`, 스냅샷 시점의 마지막 조각 순번이 고정된 읽기 참조로 제공한다. 이후 추가된 조각은 그 경계 이후의 변경으로 받는다. 과거 대화 페이지는 고정된 이력 상한과 마지막 메시지 순번을 사용하므로 새 메시지 때문에 페이지가 밀리지 않는다.

각 페이지·읽기 참조에도 접근 검증을 적용한다. 최초 제안값은 응답 본문 256KiB, 페이지당 메시지 최대 50개이며 둘 중 먼저 도달한 한도로 나눈다. 긴 단일 메시지도 조각으로 분할한다. 전체 출력·대기 버퍼·저장 공간 한도와 초과 시 오류는 첫 런타임 명세에서 함께 정한다. 기록은 보존하되 메모리·디스크가 무한하다고 전제하지 않는다.

## 8. 미확인 요청과 저장소 연속성

접수 기록은 첫 범위에서 TTL로 자동 삭제하지 않는다. 서버가 저장한 최초 접수 결과와 요청 내용 비교 정보는 Daemon 재시작 뒤에도 유지한다. `callId`·소켓·구독 번호는 연결용이므로 영속 접수 키에 넣지 않는다.

공통 클라이언트의 미확인 요청 보관에는 웹·데스크톱 공통 Web UI의 IndexedDB를 사용하는 안을 제안한다. 전송 전에 접속 대상, 인증 주체·Module 범위, Workspace, `storeEpoch`, 요청 ID·내용을 보관하고 접수 확인 시 지운다. 실제 WebView 지원·Origin 안정성·브라우저 저장소 삭제 가능성은 UI 환경에서 검증한다. 서버 기록과 같은 영속성을 보장하지 않는다.

IndexedDB는 클라이언트의 구조화 데이터를 위한 API다. 위 보관 목적과 수명은 WorkNaru의 제안이며 표준이 제품의 복구 정책을 대신 정하지 않는다. [IndexedDB 표준](https://www.w3.org/TR/IndexedDB/)

미확인 입력에는 민감한 텍스트가 있을 수 있다. 인증 토큰은 함께 저장하지 않으며 새 접속에서 다시 인증한다. 계정·Daemon이 바뀌면 이전 사본을 자동 전송하지 않는다. 저장 불가 시 전송 전에 복구 제한을 알리고, 첫 범위에서는 사용자의 명시적인 “복구 보관 없이 보내기” 선택이 있어야 전송한다. 로그아웃·사본 폐기는 미확인 요청이 있다는 사실과 확인 수단 상실을 알린 뒤 처리한다. 화면의 일반 초안 보존이나 장기 대화 캐시로 이 보관소를 사용하지 않는다.

`storeEpoch`는 “같은 접수 장부를 계속 사용하고 있는가”를 판별하는 값이다. 프로그램을 껐다 켜는 것만으로 바꾸지 않는다. DB 신규 생성, 백업 복원·교체, 접수 기록을 잃는 복구에서는 새 값으로 바꾸고 이전 epoch 요청을 자동 재전송하지 않는다. 스키마 변경만 있고 기록이 온전히 보존된 경우에는 유지한다.

이 규칙은 WorkNaru가 관리하는 복원 절차를 전제로 한다. 외부 프로그램이 DB를 과거 시점으로 조용히 되돌린 사실을 DB 내부 값만으로 항상 감지할 수는 없다. 실행 중 DB의 외부 교체·동기화는 지원하지 않으며, 기록 연속성을 확인할 수 없으면 새 접수 장부로 취급하고 자동 재전송을 막는다. 정상 조회의 `found: false`를 반환하려면 저장소·권한·epoch 확인이 모두 성공해야 한다.

## 9. 보존·백업·형식 변경

- 앱 종료, 화면 닫기, Workspace 폴더 접근 실패는 기록 삭제가 아니다. 첫 범위에서는 자동 정리와 Session·Workspace 영구 삭제 기능을 제공하지 않는다. 삭제·보존 기간은 사용자 데이터 정책과 함께 후속 설계한다.
- 로컬 DB에는 대화와 도구 입력·출력이 들어갈 수 있다. OS 사용자 접근 제한을 적용하고 인증 비밀은 별도 자격증명 저장 경계에 둔다. 일반 로그에 원문을 복제하지 않는다. DB 자체 암호화·삭제 보장은 별도 결정 대상이다.
- DB 형식 변경 전 일관된 백업을 만들고, 지원하는 순서의 마이그레이션만 트랜잭션으로 실행한다. 더 새로운 형식이나 실패한 변경을 만나면 원본을 보존하고 실행을 중단한다.
- WAL 사용 중 DB 파일 하나만 복사하거나 부속 파일을 임의 삭제하지 않는다. SQLite의 일관된 백업 방식으로 검증한 사본을 만들고, 복원은 Daemon과 관리 프로세스를 정리한 뒤 새 epoch로 개시한다. 백업 기능의 사용자 화면·일정은 이번 초안 범위가 아니다. [SQLite WAL 파일 관리](https://www.sqlite.org/wal.html)

## 10. 구현 검증 기준과 남은 결정

| 검증할 장애·경쟁 | 통과 기준 |
| --- | --- |
| 같은 요청을 웹·데스크톱에서 동시에 전송 | Run·사용자 메시지·에이전트 전달이 각각 하나다. 내용이 다르면 충돌이다. |
| 다른 요청으로 같은 Session 동시 실행 | 하나만 접수하고 다른 요청은 실행 중 오류다. |
| 접수·전달 표시·실제 전달 각 경계에서 강제 종료 | 접수 기록을 복원하며 미확인 전달을 자동 재실행하지 않는다. |
| 출력 커밋 직전·직후, 최종 결과 저장 후 알림 전 종료 | 커밋한 내용은 복원하고 미저장 내용을 보존했다고 주장하지 않는다. |
| 스냅샷 확보 중 출력 추가·완료 | 스냅샷과 이후 변경 사이에 누락·중복이 없다. |
| 승인 응답 동시 제출·전달 직후 종료·취소와 경합 | 유효한 선택은 한 번 확정하며 옛 승인 요청에 무조건 재응답하지 않는다. |
| 재시작 후 에이전트 잔존·PID 재사용·결과 불명 | 다른 프로세스를 종료하지 않으며 불명확한 Session의 새 실행을 차단한다. |
| 프로바이더 대화 불러오기 실패·전문 재생 | 저장 기록은 열람 가능하고 메시지가 중복 추가되지 않는다. |
| 디스크 부족·읽기 전용·DB 오류·버퍼 초과 | 성공을 허위 표시하지 않고 신규 실행을 차단하거나 제한된 오류로 종료한다. |
| DB 복원·스키마 변경 실패·지원 밖 버전 | 원본을 보존하고, 장부가 바뀌면 이전 epoch 요청을 자동 재전송하지 않는다. |
| 클라이언트 보관 실패·접수 응답 유실 후 새로고침 | 복구 보장 범위를 알리고, 가능한 경우 같은 요청 ID로 확인한다. |
| 긴 단일 출력·대화 이력 페이지 조회 중 새 출력 | 바이트 한도를 지키고 고정된 경계로 중복·누락 없이 조회한다. |
| 앱 전용 Daemon 종료·독립 Daemon의 UI 닫기 | 기존의 서로 다른 종료 정책을 지키며 기록은 보존한다. |

위 표는 아직 실행하지 않은 검증 기준이다. 이 초안으로 저장 원본, 논리 데이터 구조, 커밋 경계와 복구 판단 규칙을 제안한다. 구현 전에는 SQLite 연결 라이브러리·버전과 쓰기 실행 위치, SQL·런타임 스키마, 실제 데이터 경로와 단일 소유권 잠금, Windows 프로세스 정리·시간 한도, 인증 주체·Workspace 접근, 전체 자원 한도를 구체화해야 한다. 저장 설계만으로 플랫폼 초기 설계 전체가 끝난 것으로 취급하지 않는다.
