# 화면과 Daemon의 통신 설계

- 작성일: 2026-09-08
- 관련 Work Item: [#3 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 제품 개념: [README](../../README.md)
- 상위 계약: [Module과 플랫폼의 연결 규칙](module-platform-contract.md)
- 결정 근거와 상태: [ADR-0011](../adr/0011-use-websocket-for-client-daemon-communication.md)

이 문서는 상위 계약의 요청·상태 전달·재접속을 구체화한다. WebSocket 선택의 승인 범위와 결정 상태는 ADR에서 관리한다. 아래 메시지 이름·필드·시간 한도와 저장 세부 정책은 첫 구현을 위한 상세 설계안이며, 기술 선택의 승인만으로 모두 확정되거나 구현된 것은 아니다.

저장 원본·접수 커밋·재시작 판별을 구체화한 후속 초안은 [Chat의 기록 저장과 복구 설계](chat-storage-and-recovery.md)를 참고한다. 저장 방식의 결정 근거와 승인 범위는 [ADR-0012](../adr/0012-use-sqlite-for-local-platform-records.md)에서 관리한다.

## 1. 사용자에게 보이는 동작

**Chat 화면과 실제 작업을 관리하는 Daemon 사이에 양방향 연결 하나를 두고, 요청과 진행 소식을 주고받는다.** 이 연결 방식이 WebSocket이다. 사용자가 통신 기술을 직접 설정하거나 다룰 필요는 없다.

1. 사용자가 메시지를 보내면 Daemon이 접수번호와 함께 받았다고 알린다.
2. AI가 작성하는 답변과 진행 상황을 같은 연결로 계속 보여준다.
3. 승인이나 중지 버튼을 누르면 같은 연결로 Daemon에 전달한다.
4. 연결이 끊겼다가 돌아오면 현재 답변과 작업 상태를 다시 받아 화면을 복원한다.
5. 접수번호로 기존 요청을 확인해 같은 일을 두 번 시키지 않는다.

이 다섯 동작이 사용자 관점의 핵심이다. 이후 절의 호출·구독 번호와 상태 버전은 이를 구현하는 개발용 상세 사항이다.

사용자가 메시지를 보내면 화면은 Daemon에 실행을 요청한다. Daemon은 접수 여부를 즉시 알리고, AI 답변과 도구 실행 상태는 준비되는 대로 따로 전달한다. ‘중지’와 권한 승인 응답도 화면에서 Daemon으로 보내는 요청이다.

연결이 끊기면 화면에 연결 상태를 표시한다. 다시 연결되면 Daemon에서 현재 답변·실행·승인 상태를 받아 화면을 복원한다. 연결 복원을 이유로 사용자 메시지를 다시 실행하지 않는다.

Chat 화면 이동·브라우저 탭 닫기는 구독 해제이며 AI 취소가 아니다. 데스크톱 앱이 시작한 전용 Daemon은 앱의 명시적 종료 시 함께 정리한다. 독립 실행 Daemon은 접속한 앱을 닫아도 유지한다. [ADR-0002의 종료 정책](../adr/0002-use-daemon-core-with-web-and-desktop-clients.md)을 그대로 따른다.

## 2. 연결 구성과 책임

**공통 조회·명령·응답·실시간 알림은 WebSocket의 JSON 메시지로 주고받는다.** 한 클라이언트의 같은 Daemon 연결에서 여러 Module의 요청과 논리 구독을 구분한다. 웹페이지 제공과 초기 접속 등에는 HTTP를 사용할 수 있다. WebSocket은 양방향 메시지 통로이며, 요청 처리나 상태 복원 규칙은 플랫폼이 별도로 구현한다. [WHATWG WebSockets 표준](https://websockets.spec.whatwg.org/)

```text
Chat 등 Module 화면
    │ 플랫폼 기능 호출 / 상태 구독
공통 플랫폼 클라이언트
    ↕ WebSocket: 요청·응답·현재 상태·답변·도구·승인 알림
WorkNaru Daemon
    ↕ ACP
외부 AI 에이전트
```

- 공통 클라이언트가 메시지 송수신, 런타임 데이터 검증, 요청·응답 연결, 재접속과 상태 복원을 맡는다. Module마다 소켓과 전송 코드를 만들지 않는다.
- Daemon이 접근을 검증하고, 명령 접수와 실행·승인 상태를 관리한다. 명령 응답과 구독 알림은 같은 상태 원본을 사용한다.
- Module은 플랫폼 상태를 자신의 화면으로 표현하고 업무 결과의 적용 여부를 정한다. 상태 알림 수신을 보고서 수정·저장 명령으로 취급하지 않는다.
- ACP 메시지를 화면에 그대로 전달하지 않는다. Daemon에서 플랫폼의 실행·출력·도구·승인 모델로 변환한다.

Paseo도 주요 명령·알림에 WebSocket을 사용하며 요청 번호와 별도의 재접속 처리를 둔다. 이 실제 구현을 참고하되 WorkNaru의 Module 책임과 최소 Chat 범위에 맞게 설계한다. Paseo의 원격 중계·전체 프로토콜이나 모든 부가 기능을 함께 도입하는 결정은 아니다. 비교 근거와 채택 이유는 [ADR-0011](../adr/0011-use-websocket-for-client-daemon-communication.md)에 둔다.

## 3. 버전과 요청 형식

WebSocket 접속 경로는 `/ws`, 첫 전송 계약은 `protocolMajor: 1`로 제안한다. Module 등록의 `contractVersion`과 UI–Daemon 전송 버전은 서로 다른 계약이며 같은 값으로 가정하지 않는다. 호환성 변경은 새 protocol major로 구분하고 기존 필드의 의미나 필수 이벤트 종류를 같은 major 안에서 바꾸지 않는다.

초기 연결은 인증 확인 → `hello` 버전 확인 → `ready` 순서로 진행한다. 인증 절차는 7절의 후속 범위이며, 인증과 버전 확인 전에는 업무 명령을 받거나 업무 데이터를 보내지 않는다. `ready`는 `protocolMajor`, 연결마다 다른 `connectionId`, 매번 Daemon이 시작할 때 바뀌는 `daemonInstanceId`, 접수 기록의 연속성을 나타내는 `storeEpoch`, 지원 기능과 메시지·구독·버퍼 한도를 제공한다. major 불일치는 연결 오류로 알리고 종료한다. 지원하지 않는 입력 종류는 조용히 버리지 않고 거절한다.

`storeEpoch`는 정상 재시작에는 유지하고 저장소 교체·과거 백업 복원처럼 접수 기록의 연속성이 깨질 때 바꾼다. 연속성을 확인하지 못한 저장소는 신규 실행을 받지 않는다.

첫 계약은 WebSocket 텍스트 메시지 하나에 JSON 객체 하나를 담는다. 요청의 `moduleId`, `workspaceId`나 Session ID는 권한 증명이 아니다. Daemon은 인증된 호출자와 서버가 인정한 Module 호출 범위, 대상 Workspace·Session의 접근 가능 여부를 확인한다. 초기 Module 코드는 제품에 포함된 신뢰 코드이며 클라이언트의 Module 구분을 외부 코드에 대한 보안 격리로 주장하지 않는다.

모든 호출은 `type: request`, `callId`, `method`, `params`를 사용한다. 응답은 `type: response`, 같은 `callId`, `ok`와 `result` 또는 `error`를 담는다. `callId`는 한 번의 송수신을 연결하는 번호다. 명령의 `requestId`는 재접속 뒤에도 유지하는 중복 방지 번호로 구분한다. 재전송 시 `callId`는 새로 만들고 `requestId`와 명령 내용은 유지한다.

| 목적 | `method`와 핵심 입력 | 응답의 의미 |
| --- | --- | --- |
| Session 목록·단건 | `sessions.list`에 `workspaceId`, `sessions.get`에 `sessionId` | 접근 가능한 요약 또는 현재 상태 |
| Session 생성 | `sessions.create`에 `workspaceId`, 에이전트 설정 참조 | 생성된 `sessionId` |
| AI 실행 | `runs.start`에 `sessionId`, 입력 | 접수한 `requestId`, `runId`, `accepted: true` |
| 실행 조회 | `runs.get`에 `runId` | 현재 실행 상태, 확인된 결과·오류 |
| 요청 접수 확인 | `requests.get`에 `workspaceId`, 조회할 `requestId` | 같은 호출자·Module 범위의 연산·대상·접수 결과 또는 기록 없음 |
| 실행 취소 | `runs.cancel`에 `runId` | 취소 요청 접수 또는 이미 종료한 최종 상태 |
| 권한 응답 | `approvals.respond`에 `approvalId`, `optionId` | 확정된 승인 선택과 전달 상태; AI 재개 완료를 뜻하지 않음 |
| Session 실시간 구독 | `sessions.watch`에 `sessionId`, `subscriptionId` | 구독 접수 후 현재 Session 스냅샷과 이후 변경 |
| 공통 화면 실시간 구독 | `workspaces.watch`에 `workspaceId`, `subscriptionId` | 구독 접수 후 접근 가능한 Session 요약·미처리 권한 요청과 이후 변경 |
| 구독 해제 | `subscriptions.unwatch`에 `subscriptionId` | 구독 정리 확인; AI 취소를 뜻하지 않음 |

상태를 변경하는 명령에는 외피에 `requestId`와 전송 전 확인한 `storeEpoch`를 넣는다. Daemon은 저장소 연속성이 다르면 `STORE_EPOCH_MISMATCH`로 거절한다. 승인 옵션의 의미는 프로바이더 기능에 맞춰 제시하고 임의의 허용 범위를 만들어 보내지 않는다. 조회·구독의 `callId`는 영속 명령 기록을 만들지 않는다.

AI 실행 요청의 첫 지원 입력은 텍스트다. 첨부 파일·리소스 참조는 접근·크기·버전 정책을 설계한 뒤 기능으로 추가한다. 업무 데이터 연결 API는 상위 계약의 별도 후속 범위다.

```json
{
  "type": "request",
  "callId": "call_example_1",
  "method": "runs.start",
  "requestId": "req_example_1",
  "storeEpoch": "store_example_1",
  "params": {
    "sessionId": "session_example_1",
    "input": [{ "type": "text", "text": "현재 작업을 설명해줘." }]
  }
}
```

```json
{
  "type": "response",
  "callId": "call_example_1",
  "ok": true,
  "result": {
    "accepted": true,
    "requestId": "req_example_1",
    "runId": "run_example_1"
  }
}
```

`ok: true`는 해당 연산의 정상 응답이다. `runs.start`의 `accepted: true`는 처리 접수를 뜻하며 AI 작업 성공을 보장하지 않는다. 클라이언트는 최종 성공·실패를 Run 조회나 구독으로 확인한다. 소켓의 전송 함수가 성공하거나 응답 대기 시간이 끝났다는 사실만으로 Daemon의 접수 여부를 판단하지 않는다.

한 연결에서 여러 호출을 기다릴 수 있지만 `callId`는 재사용하지 않는다. 타임아웃이나 연결 종료 시 해당 대기 호출을 정리한다. 늦은 응답을 다른 호출에 연결하지 않으며, 결과가 불명확한 변경 명령은 4절에 따라 확인한다.

## 4. 요청 중복과 접수 결과 불명

요청 키는 `(인증 주체, 서버가 인정한 Module 호출 범위, workspaceId, requestId)`다. 인증·권한·저장소 연속성을 확인한 뒤 연산·대상·검증 후 정규화한 본문을 함께 비교한다. 실행 중 여부보다 키를 먼저 확인하므로 이미 접수한 실행의 재전송이 `SESSION_BUSY`로 바뀌지 않는다.

- 같은 키·같은 내용이면 최초 접수 결과와 같은 리소스 ID를 돌려준다. 응답 외피는 이번 호출의 `callId`를 사용하며, 과거 호출 번호까지 재생하지 않는다. 현재 상태는 별도로 조회한다.
- 같은 키·다른 내용이면 `REQUEST_ID_CONFLICT`다. 요청 내용에 시각 등 불안정한 값을 자동으로 보태지 않는다. `callId`와 현재 연결 번호는 명령 내용 비교에서 제외한다.
- 신규 실행 요청이면 요청 기록 생성과 Session의 실행 슬롯 확보를 원자적으로 처리한다. 같은 Session에 다른 실행이 있으면 `SESSION_BUSY`로 거절한다. 생성·취소·승인 요청도 각각의 상태 변경과 접수 기록을 원자적으로 처리한다.
- 접수 기록을 영속 저장한 뒤 외부 에이전트에 한 번 전달한다. 접수와 에이전트 전달 사이의 장애를 자동 재실행으로 숨기지 않는다.

첫 범위에서는 접수 기록을 TTL로 자동 만료시키지 않고 Daemon 재시작 뒤에도 조회할 수 있게 한다. 요청 ID는 재사용하지 않는다. Session·Workspace 삭제와 기록 정리 기능을 도입할 때 삭제 정책을 함께 결정한다. 데이터베이스는 SQLite를 사용하며, 구체적인 트랜잭션 구현은 [저장·복구 설계](chat-storage-and-recovery.md)에서 구체화한다.

공통 클라이언트는 전송 전에 요청 ID·내용·대상·Daemon 접속 대상·`storeEpoch`를 복원 가능한 로컬 보관소에 남긴다. 이는 재전송 확인을 위한 임시 입력이며 실행 상태의 원본이 아니다. 접수 확인 후 정리하고, 저장에 실패하면 새로고침 후 복구를 보장하지 못한다는 사실을 알린다. 보관소와 민감한 입력의 보존 정책은 구현 전 정한다.

연결 오류·타임아웃·불명확한 서버 오류를 받으면 재접속 후 요청 조회를 우선한다. 접수 기록이 확인되면 해당 Run이나 생성된 Session 등 연산 결과에 연결한다. `requests.get`의 정상 응답은 `storeEpoch`와 `found: true | false`를 명시한다. `found: false`이고 같은 정상 저장소임을 확인한 경우에만 같은 요청 ID·같은 내용·같은 epoch로 재전송할 수 있다. 저장소 복구·교체로 확인할 수 없으면 `REQUEST_OUTCOME_UNKNOWN` 또는 epoch 불일치를 표시하고 자동 재전송하지 않는다. 대상 없음 오류나 연결 실패만으로 실행되지 않았다고 단정하지 않는다. epoch를 임의로 현재 값으로 바꿔 미확인 요청을 재전송하지 않는다.

이 보장은 WorkNaru가 같은 요청을 중복 접수·전달하지 않도록 하는 규칙이다. 외부 도구의 파일 변경·외부 서비스 호출까지 정확히 한 번 수행된다는 보장은 아니다.

## 5. 실시간 구독과 화면 복원

첫 버전은 **구독할 때마다 현재 상태 스냅샷을 먼저 보내고, 그다음 변경을 보낸다.** 스냅샷은 ‘지금까지의 답변과 현재 상황을 한 번에 받아오는 정보’다. 이전 이벤트를 전부 재생하는 기능은 두지 않는다. 스냅샷에는 누적된 답변과 확인된 도구·실행·승인 기록이 들어가므로 연결이 끊긴 동안 생성된 결과도 복원할 수 있다.

Daemon은 화면에 확정적으로 공개할 출력·상태·승인 기록을 평상시에 영속 저장하고, 그 저장된 변경을 구독 알림과 조회에 반영한다. 짧은 출력 묶음 단위로 저장할 수 있지만 저장 실패 후에도 성공 상태나 복원 가능한 출력인 것처럼 계속 공개하지 않는다. 이는 종료 시에만 저장하지 않는 ADR-0002의 요구를 구체화한다. 기록 저장과 알림 발행 사이에 Daemon이 종료되어도 새 스냅샷에서 저장된 내용을 복원해야 한다.

공통 화면은 현재 Workspace의 요약·승인 구독 하나를 유지한다. Module 화면은 보고 있는 Session을 구독하며 같은 창 안에서 같은 Session의 구독은 공통 클라이언트가 공유한다. 첫 Chat 화면은 Session 하나를 열므로 보통 하나의 WebSocket에 두 논리 구독을 둔다. Module 화면을 닫아도 공통 승인 구독은 유지한다. Workspace를 바꾸면 이전 범위의 구독을 해제한다.

공통 클라이언트가 새 `subscriptionId`를 만들어 watch를 요청한다. Daemon은 접근과 한도를 확인한 뒤 구독 접수 응답, `snapshot`, `change` 순서로 전달한다. 같은 연결에서 같은 구독 ID·같은 대상의 재요청은 구독을 중복 생성하지 않고 최초 접수 결과를 반환한다. 다른 대상이면 `SUBSCRIPTION_ID_CONFLICT`다. 구독 해제는 여러 번 요청해도 같은 결과를 내며, 해제한 ID는 재사용하지 않는다. 확인되지 않은 구독은 해제하거나 연결을 재설정한 뒤 새 ID로 구독한다.

소켓 연결이 종료되면 서버는 그 연결의 구독만 정리한다. 클라이언트는 재접속·인증·버전 확인을 마친 뒤 아직 열려 있는 화면에 필요한 구독을 새 ID로 복원한다. AI 실행 명령은 구독과 함께 자동 재전송하지 않는다.

### 스냅샷과 변경 사이의 틈 방지

1. Daemon이 해당 구독 범위의 일관된 상태와 `revision`을 확보하면서 이후 변경 수신을 등록한다. 이 두 동작 사이에 변경이 빠질 수 없게 직렬화하거나 트랜잭션과 버퍼로 연결한다.
2. `snapshot`을 먼저 전송한다. 클라이언트는 기존 표시 상태를 이 스냅샷으로 교체한다.
3. 스냅샷을 만드는 동안 발생한 변경을 포함해 뒤이은 `change`를 순서대로 전송한다.
4. 각 변경에 `subscriptionId`, `previousRevision`, `revision`과 변경 내용을 넣는다. 이전 revision과 클라이언트 값이 일치할 때만 반영한다. 이미 반영한 revision은 무시하고, 불일치나 해석 실패가 있으면 해당 구독을 해제하고 새 스냅샷으로 복구한다.

`subscriptionId`는 새 구독마다 다르다. `revision`은 해당 구독 범위의 상태 버전이며 JSON에서는 십진수 문자열로 표현한다. Workspace와 Session의 revision을 서로 비교하지 않는다. 클라이언트는 연결과 구독 세대도 확인해 닫힌 연결이나 해제된 구독에서 늦게 도착한 데이터를 무시한다. 재접속의 새 스냅샷은 과거 구독의 revision에 이어 붙이지 않는다.

같은 소켓에서도 두 구독의 상태는 서로 다른 시점에 생성될 수 있다. Session의 상세 실행 표시는 Session 구독, 목록과 공통 승인 UI는 Workspace 구독이 갱신하며 오래된 목록 요약으로 상세 상태를 덮어쓰지 않는다. 명령 처리 시점의 최종 유효성은 항상 Daemon이 판단한다.

Session 스냅샷에는 Session 메타데이터, 현재 Run, 최근 메시지, 현재 Run의 누적 출력·도구 기록·승인 상태를 포함한다. 과거 대화는 고정된 이력 경계와 페이지 커서로 별도 조회한다. 대형 출력은 스냅샷에 크기 제한 없이 넣지 않고 버전이 고정된 읽기 참조로 제공하며, 뒤이은 변경을 버퍼링해 그 버전 이후부터 반영한다. 페이지·출력 참조 API와 한도는 저장·출력 스키마 설계에서 확정해야 한다.

다음은 각각 별도의 WebSocket 메시지로 보내는 알림 예시다. `data` 내부의 전체 도메인 스키마는 후속 구현 명세 대상이다.

```json
{
  "type": "event",
  "event": "snapshot",
  "subscriptionId": "sub_example_1",
  "scope": { "sessionId": "session_example_1" },
  "revision": "41",
  "data": { "currentRun": null, "messages": [] }
}
```

```json
{
  "type": "event",
  "event": "change",
  "subscriptionId": "sub_example_1",
  "scope": { "sessionId": "session_example_1" },
  "previousRevision": "41",
  "revision": "42",
  "data": {
    "type": "run.started",
    "sessionId": "session_example_1",
    "runId": "run_example_1",
    "requestId": "req_example_1"
  }
}
```

변경 종류는 최소한 실행 시작·상태 변경, 출력 추가, 도구 변경, 승인 요청·처리, Session 요약 갱신을 포함한다. 실행 관련 데이터에는 `sessionId`와 `runId`를 넣는다. 출력에는 안정적인 메시지·블록 ID와 위치 정보를 넣어 같은 내용을 두 번 덧붙이지 않도록 한다.

메시지 프레이밍은 WebSocket 라이브러리에 맡기고 완성된 텍스트 메시지를 JSON으로 해석한다. 구독 수, 각 메시지와 대기 데이터의 크기를 제한하고 스키마를 검증한다. 전송 순서가 유지되더라도 비동기 소비 과정에서 변경을 뒤집어 반영하지 않도록 구독별로 순서대로 처리한다.

첫 버전은 과거 알림 커서 재생을 제공하지 않는다. Paseo의 기록 보충 알고리즘을 그대로 채택하지 않고, 재구독은 새 스냅샷으로 시작한다. 모든 이벤트를 놓치지 않고 소비해야 하는 업무 자동화 용도로 이 화면 구독을 사용하지 않는다.

### 연결 유지와 느린 클라이언트

- `ready` 이후 클라이언트는 15초 간격으로 앱 수준 `ping` 메시지와 고유 nonce를 보내고 Daemon은 같은 nonce의 `pong`을 돌려준다. 이 메시지는 업무 상태를 바꾸지 않으며 WebSocket 제어 프레임의 ping·pong과 구분한다.
- 마지막 유효 pong 이후 45초간 확인이 없으면 연결을 다시 연다. 절전 중 타이머가 멈출 수 있으므로 화면 복귀 때도 연결을 확인한다. 서버도 연결 유효성과 버퍼를 제한해 응답 없는 접속을 정리한다.
- 네트워크 단절은 1초부터 최대 30초까지 지수 지연과 무작위 분산을 적용해 재시도한다. 인증·권한·버전 오류는 무한 재시도하지 않고 조치를 안내한다. 자원 제한·일시 장애의 오류 메시지에 `retryAfterMs`가 있으면 그보다 일찍 재시도하지 않는다.
- 구독별 버퍼가 한도를 넘으면 해당 구독을 종료하고 알릴 수 있는 경우 `subscription.closed`와 이유를 보낸다. 소켓 전체 송신 버퍼가 한도를 넘으면 연결을 닫는다. 복원은 새 스냅샷으로 하며, 느린 화면 때문에 에이전트 전체 실행이나 다른 클라이언트를 멈추지 않는다. 같은 소켓의 승인·응답·heartbeat가 대량 출력에 무한정 밀리지 않도록 크기 제한과 공정한 전송을 적용한다.
- 다른 호출의 응답 순서와 명령 응답·구독 알림의 생성 순서를 가정하지 않는다. `callId`, `requestId`, `runId`로 연결하고 명령 응답의 과거 접수 정보를 최신 Run 상태 위에 덮어쓰지 않는다.

시간·버퍼 수치는 초기 운영값 제안이며 성능 검증 결과가 아니다. 무제한 메모리 버퍼나 전체 대화 재전송을 전제로 삼지 않는다.

## 6. 승인·취소·실패 처리

| 상황 | Daemon과 화면의 처리 |
| --- | --- |
| 권한 요청 발생 | Daemon이 `approvalId`, 대상 Run, 요청 내용, 선택 가능한 옵션과 유효 상태를 저장하고 공통 승인 UI에 전달한다. |
| 두 화면이 같은 승인에 응답 | 원자적으로 첫 유효 선택을 확정한다. 같은 요청 ID의 재전송에는 최초 결과를, 다른 요청 ID에는 `APPROVAL_ALREADY_RESOLVED`와 확정 상태를 돌려준다. |
| 승인 후 에이전트 전달 실패 | 선택의 확정과 전달 여부를 구분해 기록한다. 전달되지 않았는데 AI가 재개됐다고 표시하지 않는다. 안전한 재전달 가능 여부는 ACP 연결 상태로 판단한다. |
| 취소 요청 | `cancelling`을 표시하고 ACP 취소를 요청한다. 실제 취소 확인 뒤 `cancelled`가 된다. 그사이 완료가 확인되면 `completed`일 수 있다. |
| 승인 대기 중 취소 | 아직 미처리인 승인은 닫고 에이전트가 기다리는 권한 요청도 거절·취소로 정리한다. 뒤늦은 허용은 `APPROVAL_EXPIRED`로 거절한다. 이미 확정된 승인을 취소가 소급해서 무효화했다고 주장하지 않는다. |
| 실행 종료와 늦은 이벤트 | 최종 상태를 한 번 확정한다. 뒤늦은 승인이나 출력이 Run을 다시 실행 중으로 바꾸지 못하게 한다. |
| UI 연결 단절 | 연결 상태만 바꾼다. Run을 자동으로 실패·취소 처리하지 않는다. |
| Daemon 비정상 종료 | 새 `daemonInstanceId`로 재접속하고 저장된 기록을 복원한다. 실행 중이던 작업은 실제 프로세스·프로바이더 상태를 조사하며 자동 재실행하지 않는다. |

실행 복구를 확인하는 동안에는 연결·복구 상태를 별도로 표시하고 해당 Session의 새 실행을 막는다. 프로세스 정리가 확인되었으나 최종 결과를 확인할 수 없으면 `failed`와 `EXECUTION_OUTCOME_UNKNOWN`을 기록한다. 남은 프로세스의 실행 여부조차 불명확하면 차단을 유지하고 사용자에게 안내한다. 이 오류는 외부 파일 변경이 없었다는 뜻이 아니다. 조사·정리의 구체적인 시간 한도와 프로바이더 복구 방법은 후속 저장·프로세스 설계가 필요하다.

이 설계는 기존 Run 상태 집합을 유지한다. ‘접속 끊김’, ‘동기화 중’, ‘복구 확인 중’은 별도의 클라이언트·가용성 정보다. 화면 복원과 AI 작업의 실제 재개를 구분한다.

## 7. 오류와 접근 경계

연산 오류는 `type: response`, 해당 `callId`, `ok: false`, `error.code`, 사용자에게 보여줄 `error.message`를 포함한다. 확인 가능한 명령에는 `requestId`도 연결한다. 내부 경로·스택·인증정보는 그대로 보내지 않는다. 검증 오류는 `INVALID_REQUEST`, 권한 부족은 `FORBIDDEN`, 존재하지 않거나 노출할 수 없는 대상은 `NOT_FOUND`, 크기 초과는 `MESSAGE_TOO_LARGE`, 자원 제한은 `RATE_LIMITED`, 일시 장애는 `UNAVAILABLE`로 구분한다. 실행 충돌 등은 앞 절의 구체적인 오류 코드를 사용한다. 일반 서버 오류만 보고 명령이 접수되지 않았다고 판단하지 않는다.

해석할 수 없는 메시지나 과대 메시지처럼 호출 번호조차 신뢰할 수 없는 경우에는 제한된 연결 오류를 알리거나 소켓을 종료한다. 다른 정상 연산의 업무 오류 때문에 연결 전체를 닫지는 않는다. 인증·버전 등 연결 전반의 오류는 `connection.error`로 안내 가능한 범위만 전송한 뒤 종료한다. HTTP 업그레이드 단계의 오류는 이 JSON 응답과 구분하며, 소켓 종료를 AI 취소로 해석하지 않는다.

모든 명령·조회·구독에 같은 접근 검증을 적용한다. WebSocket 연결을 만들 때만 검사하고 영구 허용하지 않으며 권한 철회·인증 만료 시 관련 구독과 데이터 전달을 종료한다. Module에 필요한 기능이 선언되어 있어도 자동 승인하지 않는다.

첫 연결 범위는 로컬 Daemon이다. loopback에만 바인딩하고 업그레이드의 허용 Host·Origin을 검증한다. 로컬 주소나 브라우저의 CORS 정책만으로 WebSocket 인증을 대신하지 않는다. 인증정보는 URL·구독 알림·Module 입력에 넣지 않는다. Cookie를 사용하게 되면 다른 사이트가 그 Cookie로 소켓을 여는 공격을 막도록 명시적인 Origin·초기 연결 검증이 필요하다.

인증정보의 발급·전달·폐기, Web UI 제공 Origin과 데스크톱 WebView의 접속 방식은 후속 접근 설계에서 확정한다. 브라우저 WebSocket 생성자에 임의 HTTP 인증 헤더를 설정할 수 있다고 가정하지 않는다. 인증된 접속을 마련하는 경계를 두되 이를 인증 설계 완료로 간주하지 않는다. 초기 인증의 시간·메시지 한도와 실패 종료도 함께 설계한다. 원격 공개·다중 사용자·외부 Module 설치는 첫 연결 검증에 포함하지 않는다.

## 8. 구현 시 검증할 사례와 남은 사항

| 검증 사례 | 통과 기준 |
| --- | --- |
| 첫 메시지 전송 | 요청 접수, 점진적 답변, 최종 결과가 같은 Run으로 연결된다. |
| 같은 요청 동시 전송·같은 ID의 다른 내용 | 실행은 하나만 만들어지고, 내용 충돌은 거절된다. |
| 다른 요청으로 같은 Session 동시 실행 | 하나만 접수하고 나머지는 `SESSION_BUSY`다. |
| 명령 응답 유실·응답보다 실행 알림이 먼저 생성 | 요청 조회와 ID 연결로 중복 실행·중복 메시지를 만들지 않는다. |
| 스냅샷 생성 중 출력·완료 발생 | 스냅샷 또는 후속 변경에 반영되고, 경계에서 누락되지 않는다. |
| 새로고침·연결 중단·Module 이동 | 현재 답변과 최종 상태를 복원하며, 이전 연결의 늦은 데이터는 무시한다. |
| 한 소켓의 여러 호출·구독이 섞여 도착 | 호출·구독 번호로 정확하게 전달하고 다른 화면 상태를 덮어쓰지 않는다. |
| 구독 응답 유실·해제 뒤 늦은 알림·재접속 | 구독을 중복 생성하지 않고 닫힌 구독 알림을 무시하며 현재 화면의 구독만 복원한다. |
| 잘못된 JSON·과대 메시지·응답 없는 연결 | 제한된 오류·버퍼·종료 처리로 자원을 보호한다. |
| 느린 화면·버퍼 초과·큰 대화 | 버퍼를 제한하고 복원하며, 다른 클라이언트와 AI 실행을 막지 않는다. |
| Chat을 닫은 상태에서 승인 필요 | 현재 Workspace의 공통 승인 UI에 표시된다. |
| 승인 경쟁·취소 경쟁 | 승인 선택 한 번만 확정, 실제 결과에 맞는 Run 최종 상태를 표시한다. |
| 접수 저장 직후·에이전트 전달 직후 장애 | 같은 요청을 자동 재실행하지 않고 기록과 실제 실행을 조사한다. |
| 접근 불가 Session·권한 만료·잘못된 버전 | 명령·조회·구독 모두 거절하고 정보가 새지 않는다. |
| 데스크톱 전용·독립 실행 Daemon 종료 | ADR-0002의 서로 다른 종료 정책을 지킨다. |

위 표는 테스트 수행 결과가 아닌 구현 검증 기준이다. WebSocket 선택만으로 신뢰성이나 복구가 완성되지는 않는다.

후속으로 저장소와 원자적 기록 방법, 전체 요청·이벤트 런타임 스키마, 이력 페이지·대형 출력 참조와 한도, 클라이언트 미확인 요청 보관, 인증 초기 연결, ACP 장애 복구를 정해야 한다. 라이브러리·서버 프레임워크·UI 프레임워크는 이번 제안의 범위가 아니다. 해당 항목을 해결하거나 첫 구현 범위를 합의하기 전에는 제품 구현 준비가 모두 끝났다고 판단하지 않는다.
