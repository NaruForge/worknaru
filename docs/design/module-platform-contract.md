# Module과 플랫폼의 연결 규칙

- 작성일: 2026-09-08
- 관련 Work Item: [#3 플랫폼 초기 아키텍처 설계](https://github.com/NaruForge/worknaru/issues/3)
- 제품 개념의 원본: [README](../../README.md)
- 연결 규칙의 결정 근거: [ADR-0009](../adr/0009-use-a-common-module-platform-contract.md)

이 문서는 Module과 플랫폼의 연결 구조, 동작 기준과 첫 검증 범위를 설명한다. 결정 근거와 상태는 해당 ADR에서, 작업 진행은 GitHub Project에서 관리한다. 아래의 연산 이름과 데이터 표현은 상세 설계를 위한 설명용이며 실제 API 이름·전송 형식의 확정이나 구현 완료를 뜻하지 않는다. 후속으로 명시한 사항은 별도로 설계한다.

요청·실시간 상태 전달·재접속을 구체화한 후속 내용은 [화면과 Daemon의 통신 설계](client-daemon-protocol.md)를 참고한다. 전송 방식의 결정 근거와 상태는 [ADR-0011](../adr/0011-use-websocket-for-client-daemon-communication.md)에서 관리한다.

평상시 기록과 재시작 시 처리 규칙의 후속 초안은 [Chat의 기록 저장과 복구 설계](chat-storage-and-recovery.md)를 참고한다.

## 1. 쉽게 보는 연결 방식

Module은 자신의 업무를 맡고, 공통 기능이 필요할 때 플랫폼에 요청한다. 플랫폼은 요청을 확인하고 실행 상태와 결과를 돌려준다.

| 연결 단계 | Chat의 예 | 플랫폼이 하는 일 |
| --- | --- | --- |
| 등록 | “나는 Chat이며 대화 화면을 제공합니다.” | Module 정보를 확인하고 사용 가능한 서비스 목록에 등록 |
| 화면 열기 | “사용자가 Chat을 선택했습니다.” | 공통 화면 안에서 Chat 화면을 열고 현재 작업 환경을 전달 |
| 작업 요청 | “이 Session에서 사용자의 메시지를 처리해 주세요.” | 대상과 권한을 확인하고 AI 실행을 시작 |
| 상태·결과 전달 | “응답을 표시하고, 필요하면 사용자의 다음 입력을 받습니다.” | 응답 조각, 도구 실행 상태, 승인 요청과 완료·실패를 전달 |

보고서 생성 Module도 같은 통로로 AI를 사용하되, 결과를 대화 화면 대신 보고서 초안이나 수정 제안으로 보여준다. 업무 내용을 언제 저장하고 확정할지는 해당 Module이 정한다.

## 2. 기존 결정에서 가져오는 경계

- Module은 업무 서비스이며, 업무 화면·규칙·데이터와 결과를 소유한다. [ADR-0006](../adr/0006-define-modules-as-business-services.md)
- 업무 데이터와 AI Session은 별도로 관리하고 필요에 따라 연결한다. [ADR-0007](../adr/0007-separate-business-data-from-ai-sessions.md)
- Chat은 첫 기본 제공 Module이다. 다른 Module은 Chat을 거치지 않고 플랫폼의 AI 기능을 사용한다. [ADR-0008](../adr/0008-provide-chat-as-a-default-module.md)
- 웹과 데스크톱은 같은 WorkNaru Daemon의 상태와 실행 기능을 사용한다. Agent 내부 실행은 Paseo에 위임하도록 결정했으며, Module은 기존처럼 플랫폼 계약을 사용한다. [ADR-0016](../adr/0016-use-paseo-for-agent-management.md). 현재 코드는 Migration 전 ACP 구현이다.

이 설계는 위 경계를 바탕으로 Module 등록 정보와 공통 기능 호출·상태 전달 계약을 구체화한다. UI 프레임워크, 전송 기술, 데이터베이스나 Module의 실행 언어는 선택하지 않는다.

## 3. 구성과 실행 위치

```text
웹 브라우저 또는 데스크톱의 공통 Web UI
  공통 화면: Module 목록, 화면 전환, 권한 승인 표시
    └─ Module 화면: Chat / 보고서 / 문서 정형화
          └─ 플랫폼 기능 호출·상태 구독
                      ↕ 공통 클라이언트–Daemon 계약
WorkNaru Daemon
  호출 검증 / Workspace 접근 / Session·AI 실행 / 상태·기록
                      ↕ ACP 연결
외부 AI 에이전트
```

‘공통 화면’은 클라이언트에서 Module 화면을 열고 닫는 플랫폼 부분을 가리킨다. AI 실행과 공유 상태의 원본은 Daemon에 있다. 도식의 Module 화면은 업무 서비스의 UI 부분이며, Module의 모든 업무 처리가 브라우저에서 실행된다는 뜻은 아니다. 문서 파싱·내보내기 같은 업무 처리의 실행 위치는 후속 설계 대상이다.

## 4. Module 등록과 화면 수명

### 등록 정보

Module은 다음 정보를 선언하고, 플랫폼은 사용할 수 있는 등록인지 확인한다.

| 항목 | 의미 | Chat 예시 |
| --- | --- | --- |
| `moduleId` | 표시 이름이 바뀌어도 유지하는 고유 식별자 | `chat` |
| `displayName` | 사용자에게 표시할 서비스 이름 | `Chat` |
| `contractVersion` | 이 Module이 요구하는 연결 계약 버전 | 첫 계약의 버전; 실제 값은 구현 전 선정 |
| `views` | 화면 식별자·이름과 제품이 확인한 화면 진입점 | 대화 화면 |
| `requiredCapabilities` | 반드시 필요한 플랫폼 기능 | Session 조회·생성, AI 실행·구독·취소 |
| `optionalCapabilities` | 있으면 사용하는 추가 기능 | 추후 지원할 첨부 자료 접근 등 |

기본 제공 여부는 설치·배포를 관리하는 플랫폼 정보로 둔다. Module의 자체 선언만으로 기본 제공 출처나 권한을 인정하지 않는다. 같은 `moduleId`의 중복 등록, 호환되지 않는 계약 버전, 필수 기능 누락은 조용히 대체하지 않고 등록 오류로 표시한다. 선택 기능이 없으면 해당 UI를 비활성화하거나 지원하지 않는 이유를 안내한다.

첫 검증에서는 제품에 포함된 Chat을 명시적으로 등록한다. 임의 폴더의 코드를 자동 탐색하거나 외부 Module을 설치하는 기능은 첫 검증 범위에 포함하지 않는다. 이것은 등록 계약의 사용 사례이며 영구적인 배포 방식의 확정은 아니다.

### 화면 열기와 닫기

플랫폼은 화면을 열 때 현재 `workspaceId`, 화면별 탐색 정보, 사용할 수 있는 플랫폼 기능을 전달한다. Module은 화면을 구성하고 필요한 Session 상태를 구독한다. 폴더 경로만으로 호출 권한을 판단하지 않으며, 실제 Workspace 식별·경로 판별은 후속 설계에 따른다.

화면을 닫거나 다른 Module로 이동하면 화면의 구독과 UI 자원을 해제한다. 이것을 AI 취소, Session 삭제 또는 Module 제거로 취급하지 않는다. 저장하지 못한 업무 입력이 있다면 Module이 이동을 보류할 수 있도록 공통 화면에 알리는 계약을 둔다.

Module 전체를 비활성화·제거하는 기능은 화면 닫기와 구분하며, 진행 중인 업무와 데이터 처리 정책이 정해지기 전에는 첫 검증에 포함하지 않는다. 데스크톱 앱·Daemon 자체의 종료는 [ADR-0002](../adr/0002-use-daemon-core-with-web-and-desktop-clients.md)의 실행 방식별 정책을 그대로 따른다.

## 5. 공통 기능 호출

아래 이름은 기술 선택과 무관한 설명용 연산이다. HTTP 주소, WebSocket 메시지 또는 실제 SDK 함수명을 확정하지 않는다. 요청에는 플랫폼이 검증한 호출자·Module·작업 환경이 연결되며, 요청 본문의 `moduleId`나 리소스 식별자만으로 접근을 허용하지 않는다.

| 연산 | 요청의 핵심 정보 | 돌려주는 정보·효과 |
| --- | --- | --- |
| `sessions.list / get` | 조회 범위 또는 `sessionId` | 접근 가능한 Session 요약, 상태와 사용 가능한 AI 기능 |
| `sessions.create` | 대상 `workspaceId`, 사용할 에이전트 설정 참조 | 플랫폼의 `sessionId`; 생성 실패 시 이유 |
| `links.list / attach / detach` | `businessRef`, `sessionId` | 해당 업무 데이터와 Session의 연결 조회·변경 |
| `runs.start` | `requestId`, `sessionId`, 입력, 필요한 자료, 선택적인 `businessRef` | 접수된 `runId` 또는 명확한 거절 이유 |
| `runs.get` | `runId` 또는 호출자가 보관한 `requestId` | 현재 실행 상태와 확인 가능한 결과·오류 |
| `runs.cancel` | `runId` | 취소 요청 접수 여부; 실제 종료는 후속 상태로 확인 |
| `sessions.watch` | `sessionId` | 일관된 현재 상태와 이후 변경 알림, 구독 해제 수단 |
| `approvals.respond` | `approvalId`, 선택한 허용·거절 응답 | 플랫폼 공통 승인 UI에서 제출; 처리 결과는 관련 화면에 전달 |

`runs.start`에 넘기는 `businessRef`는 실행의 업무상 출처를 표시한다. 지속적인 Session 연결은 `links.attach`로 별도 관리한다. Session 생성이나 AI 실행이 보고서 객체를 자동으로 만들거나 삭제하지 않도록 한다. Chat은 보고서 같은 별도 업무 객체를 만들지 않고 Session을 사용할 수 있다.

연결 요청에서 업무 데이터의 존재와 유효성은 소유 Module이 확인하고, 플랫폼은 호출 범위와 대상 Session의 접근 가능 여부를 검증해야 한다. 업무 참조를 보유했다는 이유만으로 그 본문을 읽거나 다른 Module의 Session을 사용할 수 있게 하지 않는다. 구체적인 접근 규칙과 삭제 후 참조 정리는 후속 설계에서 정한다.

### 식별자와 자료 전달

- `sessionId`: 대화와 후속 작업의 맥락을 식별한다. 에이전트 프로세스 ID나 프로바이더 내부 식별자와의 대응은 플랫폼 내부에서 다룬다.
- `runId`: 이 설계에서는 Session에 입력을 보내 시작한 한 번의 AI 실행을 식별한다. 보고서 작성 전체를 뜻하지 않는다. Module의 한 업무 흐름이 여러 AI 실행과 수동 단계를 포함할 수 있다.
- `requestId`: 요청한 쪽이 응답을 잃었을 때 같은 요청의 접수 여부를 확인하는 값이다. 같은 호출 범위에서 같은 ID와 같은 내용의 재전송은 새 실행을 만들지 않도록 한다. 같은 ID에 다른 내용을 보내면 거절한다. Daemon 재시작까지 포함한 보존 범위는 저장 설계에서 정한다.
- `businessRef`: 업무 데이터 참조를 `workspaceId`, `moduleId`, `entityType`, `entityId`로 표현한다. 플랫폼은 연결과 접근을 관리하고, `entityType`의 업무 의미나 실제 본문 구조는 Module이 해석한다. 이 형태가 모든 Module에 적합한지는 후속 사례로 검토한다.

입력에는 사용자 요청과 Module이 준비한 업무 맥락을 담는다. 자료는 실제 텍스트나 접근 검증이 가능한 리소스 참조로 전달하며, 문서 식별자만 전달했다고 AI가 내용을 알게 되는 것으로 가정하지 않는다. 편집 중인 보고서 등 변경 가능한 자료는 어떤 버전의 내용으로 실행했는지 함께 기록한다.

리소스 참조를 통해 자료를 전달하는 형식, 크기 제한과 파일 접근 정책은 후속 상세 설계가 필요하다. 프로바이더가 지원하지 않는 입력·출력 기능은 실행 전에 알리며 조용히 누락하지 않는다. 인증정보는 Module 입력이나 결과에 포함하지 않는다.

### 상태와 결과 전달

논리적인 실행 상태는 `running`, `waiting_for_approval`, `cancelling`, `completed`, `failed`, `cancelled`로 표현한다. 실행 전 거절은 상태 전이가 아닌 요청 오류다. AI 실행의 `completed`는 AI 응답 완료이며, Module의 보고서 저장·검토·확정 완료를 의미하지 않는다.

출력 조각, 도구 실행 정보, 상태 변화와 승인 요청에는 관련 `sessionId`, `runId`, 중복 판별과 순서 확인 정보를 붙인다. 화면은 이를 표시하고, 다시 받은 알림만으로 보고서 수정 같은 업무 처리를 재실행하지 않는다. 최종 상태와 확인 가능한 결과는 구독을 놓쳐도 조회할 수 있어야 한다.

첫 구현에서는 같은 Session에 한 번에 하나의 AI 실행만 허용하고, 실행 중 추가 요청에는 실행 중임을 알리는 오류(설명용 이름: `SESSION_BUSY`)를 돌려준다. 자동으로 대기열에 넣거나 기존 실행을 취소하지 않는다. 다른 Session의 실행과 자원 한도는 별도로 관리한다. 사용자는 기존 실행이 끝난 뒤 입력하거나 명시적으로 취소할 수 있다.

## 6. Chat으로 따라가는 한 번의 실행

1. 플랫폼이 Chat 등록 정보를 확인하고 서비스 목록에 표시한다.
2. 사용자가 작업할 Workspace에서 Chat을 연다. Chat은 해당 범위에서 접근 가능한 Session을 조회하거나 새 Session을 만든다.
3. 사용자가 메시지를 보내면 Chat은 `requestId`와 입력을 보관하고 `runs.start`를 요청한다. Daemon은 대상·기능 지원·권한을 검사하고 실행을 접수한다.
4. Chat은 `runId`에 해당하는 응답 조각과 도구 실행 상태를 표시한다. 공통 상태는 Daemon이 소유한다.
5. 도구 실행 권한 승인이 필요하면 공통 승인 UI가 요청 내용을 보여준다. 사용자의 응답을 플랫폼이 처리하고, Chat은 대기·재개 상태를 표시한다.
6. 사용자가 중지를 누르면 `runs.cancel`을 요청한다. Chat은 즉시 완료로 표시하지 않고 실제 종료 상태를 기다린다.
7. 완료·취소·실패 상태와 확인 가능한 기록을 표시한다. 사용자가 화면을 다시 열면 Session 상태를 다시 조회한다.

Chat의 화면 설정이나 대화 목록 표시 방식은 Chat이 소유한다. 플랫폼이 관리하는 실행·승인 기록의 별도 원본을 Chat에 만들지 않는다. 프로바이더가 보존하는 대화의 불러오기 범위는 기존 ACP 연결 결정에 따른다.

## 7. 사용자 개입, 실패와 재접속

| 상황 | 처리 기준 |
| --- | --- |
| 권한 승인 | Daemon이 승인 요청의 대상과 유효 상태를 소유한다. 공통 UI의 사용자 응답만 처리하며 Module이 사용자를 대신해 자동 승인하지 않는다. 거절은 에이전트에 전달하고 이후 실제 실행 상태를 따른다. |
| 웹과 데스크톱에서 같은 승인에 응답 | 첫 유효 응답을 한 번 처리하고 다른 응답에는 이미 처리됨을 알린다. 모든 관련 화면에 같은 결과를 전달한다. |
| 취소와 완료가 동시에 발생 | Daemon이 확인한 최종 상태를 표시한다. 취소 요청 접수와 취소 완료를 구분하고, 이미 수행한 파일 변경을 자동 원복했다고 표시하지 않는다. |
| 전송 직후 연결 끊김 | 접수 여부가 불명확하면 `requestId`로 조회한다. 자동으로 새 ID를 만들어 재실행하지 않는다. 기록을 확인할 수 없으면 결과 불명 상태를 안내한다. |
| 화면 새로고침·Module 이동 | 화면 구독만 정리한다. 재접속 시 현재 상태와 이후 알림을 누락 없이 이어받을 수 있는 구독 계약이 필요하다. 단순 재연결을 새 실행으로 취급하지 않는다. |
| 에이전트 또는 Daemon 비정상 종료 | 실제 실행 상태를 다시 확인한다. 완료 근거가 없으면 성공으로 처리하지 않고 실패·중단 여부를 안내한다. 자동 재실행과 프로바이더 세션 복구는 별도 정책을 따른다. |
| 업무 결과 저장 실패 | Module이 결과와 입력을 보호하고 저장 재시도를 제공한다. AI 실행의 성공과 업무 저장의 실패를 별도로 표시한다. |

재접속은 실행 상태 조회와 화면 복원을 위한 계약이다. 상태 조회 시점과 실시간 알림 구독 사이의 변경을 놓치지 않도록 해야 하며, 구체적인 순번·스냅샷·저장 방식은 전송·저장 설계에서 정한다. 브라우저 탭 닫기를 Daemon 종료로 취급하지 않는 기존 정책을 유지한다.

## 8. 다른 Module에 적용한 문서상 검토

| 항목 | 보고서 생성 | 문서 정형화 |
| --- | --- | --- |
| AI 없이 하는 업무 | 보고서 생성·편집·저장 | 원문 대조·구조 수정·검토 |
| AI 요청 예 | 목적·참고 자료·작성 설정을 전달해 초안 요청 | 사용자가 선택한 문서 내용과 원문 근거를 전달해 구조 수정 제안 요청 |
| 업무 연결 | 보고서의 `businessRef`와 작성·검토 Session을 연결 | 검토 문서의 `businessRef`와 지원용 Session을 연결 |
| Module이 결과를 처리하는 방식 | 초안 또는 수정안으로 표시하고 업무 규칙에 따라 반영 | 원문과 대조 가능한 제안으로 표시하고 검토자의 판단에 따라 반영 |
| 사람이 판단할 사항 | 보고서 수정안 적용·최종 내용 확인 | 의심 항목 판정·확정본 생성 조건 충족 |

문서 정형화의 AI 단계는 향후 기능을 가정한 설계 검토다. 현재 DocCan 구현을 검증했다는 의미가 아니다. 두 서비스 모두 AI 호출에 Chat을 경유할 필요가 없으며, AI 응답만으로 업무상 검토 완료를 선언하지 않는다.

검토상 필요한 공통 정보는 Session·실행·입력·출력·승인 상태와 업무 참조다. 보고서 목차나 문서 표 구조는 공통 AI 계약의 필수 필드가 되지 않는다. 실행 도중 업무 내용이 바뀌었다면 Module이 요청 당시 버전과 현재 버전을 비교해 결과 적용 여부를 판단해야 한다.

이 검토는 데이터 구조와 흐름의 적합성을 보는 문서상 검토다. 기존 TypeScript·Python 업무 코드를 어떻게 실행·연결할지는 해결하지 않았으며, 전체 Module 이식 가능성을 입증하지 않는다.

## 9. 첫 구현으로 검증할 범위와 남은 설계

첫 검증 범위는 Chat 하나의 명시적 등록, 화면 열기·구독 해제, Session 생성·조회, 메시지 전송·응답 표시, 권한 승인, 취소·실패 표시와 UI 재접속이다. 업무 데이터 연결은 보고서·문서 정형화의 문서상 예시로 먼저 검토하고, 실제 Module 도입 시 구체화한다.

Module이 요구하는 기능 선언은 자동 권한 부여가 아니다. 공통 API는 호출 대상과 접근을 검증해야 한다. 같은 프로세스에서 실행하는 코드에 기능 객체를 전달하는 것만으로 보안 격리가 생기지는 않으므로, 외부 코드를 받기 전 신뢰 모델과 실행 격리를 별도로 결정해야 한다.

| 후속 설계 | 정해야 하는 내용 |
| --- | --- |
| 호출·전송·버전 | 클라이언트–Daemon 프로토콜, 입력 검증, 계약 버전 호환, 요청 ID 보존 범위 |
| 저장·복구 | 상태·출력·승인 기록의 평상시 저장, 재접속 일관성, 비정상 종료 후 판별 |
| Workspace·Session 접근 | 소속 상세, 호출자 인증, 업무·Module 간 공유와 링크 접근·삭제 정책 |
| 업무 실행·저장 | Module의 업무 코드 실행 위치, 데이터 저장 인터페이스, 편집 버전 충돌 처리 |
| Module 관리 | 활성화·해제·제거, 실행 중 변경, 외부 설치·신뢰·권한과 배포 방식 |

외부 Plugin 설치, 범용 업무 흐름 엔진, 스케줄링과 Module 간 Session 공유는 첫 검증 범위에서 보류한다. 이 문서는 #3 전체 설계의 일부이며, 위 후속 설계를 해결하거나 범위를 합의하기 전에는 구현 준비가 모두 끝났다고 판단하지 않는다.

## 10. 구현 시 확인할 사례

| 검증 사례 | 기대하는 결과 |
| --- | --- |
| 중복 Module ID·지원하지 않는 계약 | 기존 Module을 덮어쓰지 않고 오류 표시 |
| AI 없이 문서 편집 | 불필요한 Session 생성 없이 업무 데이터 저장 가능 |
| 입력 전송·응답 수신 | 요청한 Session과 실행에 해당하는 출력만 표시 |
| 같은 요청 재전송·동시 실행 요청 | 중복 실행 방지, 실행 중 추가 요청의 명확한 거절 |
| 권한 거절·두 클라이언트의 승인 경쟁 | 유효 응답 한 번만 처리, 공통 상태 일치 |
| 화면 닫기·다시 열기 | 실행·업무 데이터 보존, 현재 상태와 후속 알림 복원 |
| 취소·에이전트 실패·Daemon 종료 | 실제 결과에 맞는 상태 표시, 성공으로 오인하지 않음 |
| 보고서 수정 중 AI 결과 도착 | 과거 버전의 결과가 현재 편집 내용을 자동으로 덮어쓰지 않음 |

위 항목은 후속 구현의 검증 기준이며, 테스트 수행 결과나 완료 체크리스트가 아니다.
