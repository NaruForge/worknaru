# 초기 저장소 구성과 책임 경계 설계안

- 작성일: 2026-09-08
- 관련 Work Item: [#5 저장소 구조와 코드 의존 규칙 설계](https://github.com/NaruForge/worknaru/issues/5)
- 제품 방향과 책임: [README](../../README.md)
- 저장소·패키지 선택의 근거: [ADR-0013](../adr/0013-start-with-one-package-and-explicit-code-boundaries.md)
- 참고 자료: [저장소 구조 조사](../research/2026-09-08-repository-architecture.md)

Paseo로 Agent 관리를 위임하는 결정은 [ADR-0016](../adr/0016-use-paseo-for-agent-management.md)을 따른다. 1~5절은 초기 설계의 기록이며, 현재 Paseo 기반 구현의 책임 배치는 6절에 설명한다.

## 1. 지금 정할 범위

**이 설계는 저장소의 출발 방식과 큰 책임 경계만 다룬다. 상세 폴더·파일 배치는 첫 기능을 구현하면서 정한다.** 코드가 없는 상태에서 미래 영역의 디렉터리, 공개 함수, 테스트 파일과 실행 명령까지 미리 정하지 않는다.

첫 적용 범위는 [#3에서 합의한](https://github.com/NaruForge/worknaru/issues/3) 메시지 접수 → SQLite 저장 → 데몬 재시작 후 조회다. 실제 AI 연결과 Chat 화면은 이후 단계에서 연결한다. 구조 설계의 상세화를 첫 구현의 착수 조건으로 삼지 않는다.

## 2. 저장소의 출발 방식

현재 저장소에서 첫 Daemon을 하나의 패키지로 시작한다. 이 선택의 근거와 상태는 ADR-0013에서 관리한다.

| 대안 | 판단 근거와 비용 |
| --- | --- |
| 한 저장소·하나의 초기 패키지 | 첫 구현의 설정과 실행을 작게 시작할 수 있다. 실제 코드가 늘 때 필요한 분리를 판단해야 한다. |
| 한 저장소·여러 패키지 | 서로 다른 빌드·의존성을 관리하기 좋지만, 현재는 아직 필요하지 않은 패키지의 설정까지 생길 수 있다. |
| 별도 저장소로 분리 | 독립 권한·릴리스가 필요할 때 유용하지만, 지금은 계약과 버전을 따로 맞추는 비용이 추가된다. |

폴더, 패키지, 프로세스와 배포물은 서로 다른 구분이다. 하나의 패키지로 시작한다고 Daemon과 화면을 같은 프로세스로 실행하거나 모든 기능을 한 파일에 넣는다는 뜻은 아니다. 별도 빌드·배포 등 실제 필요가 생기면 해당 부분의 분리를 검토한다.

## 3. 유지할 책임 경계

아래는 기존 제품 정의와 설계에서 가져온 역할이다. 각 행을 별도 폴더나 패키지로 만들라는 지시가 아니다.

| 역할 | 책임 |
| --- | --- |
| 플랫폼 Daemon | 접근 검증, Workspace·Session·실행과 공통 기록 관리 |
| 공통 접속 기능 | 화면과 Daemon 사이의 요청·응답·상태 전달 |
| 공통 작업 화면과 앱 | Module을 열고 플랫폼 기능을 연결하며 앱의 실행 방식을 제공 |
| Chat 등 업무 Module | 자신의 화면·업무 규칙·업무 데이터와 결과 활용 |

Module은 플랫폼이 제공하는 기능을 사용하고, 플랫폼의 내부 DB나 에이전트 구현에 직접 기대지 않는다. 플랫폼의 공통 실행 기능은 특정 Chat 화면에 종속되지 않는다. 구체적인 코드 연결 방법은 실제 호출을 구현할 때 정한다. [Module과 플랫폼의 연결 규칙](module-platform-contract.md)

예를 들어 보고서 Module은 편집과 수정안 적용을 맡고 AI가 필요할 때 플랫폼에 요청한다. Chat을 거칠 필요가 없으며 Session을 닫아도 보고서 데이터는 남는다. 이 사례의 서버 실행·업무 저장 방식은 해당 Module을 구현할 때 구체화한다.

## 4. 첫 구현에서 확인할 흐름

1. **접수:** Daemon이 요청과 대상 접근을 확인한다.
2. **저장:** 플랫폼이 접수 결과와 관련 기록을 SQLite에 함께 저장하고, 저장 성공 후 접수를 알린다.
3. **재시작 조회:** 새 Daemon 프로세스에서 커밋한 기록을 다시 읽고 같은 요청으로 기록을 중복 생성하지 않는지 확인한다.

통신과 저장의 상세 참고 자료는 [통신 설계](client-daemon-protocol.md)와 [저장·복구 설계](chat-storage-and-recovery.md)다. 인증·접근 검증, 실제 데이터 경로, DB 단일 소유권과 SQL·런타임 스키마는 첫 구현에서 필요한 만큼 구체화한다. 실제 AI 실행과 복구는 별도 연결 단계에서 검증한다.

현재는 **폴더·import 경계·순환 의존 등을 강제하는 구조 검사와 이를 위한 도구·CI·별도 수동 점검 절차를 도입하지 않는다.** 기능에 필요한 타입 검사와 저장·중복 방지·재시작 조회 등의 동작 검증은 수행한다. 테스트 파일 배치와 실행 명령은 구현할 코드와 도구가 정해질 때 마련한다.

## 5. 파일 관리와 이후 결정

- 기존 문서와 프로젝트 운영 파일의 위치를 유지한다.
- 소스와 필요한 테스트는 버전 관리하고, 생성물·개발 임시 파일·실행 데이터와 인증정보는 구분한다. 구체적인 경로와 무시 설정은 해당 파일이 필요해질 때 정한다.
- 현재 작업에서는 제품 코드·빈 폴더·패키지를 생성하지 않는다. 구현에서도 필요한 코드부터 추가하고 실제 공유 요구가 생겼을 때 공통화한다.
- UI·데스크톱 프레임워크, 향후 패키지 분리와 Module 업무 저장 방식은 해당 기능을 구현할 때 결정한다.

이 설계의 검토 대상은 첫 구현에 충분한 출발 방식과 책임 구분이다. 상세 디렉터리 트리나 구조 검사 방법을 완성하는 것은 현재 완료 조건으로 두지 않는다.

## 6. 현재 구현의 책임 배치

[#35](https://github.com/NaruForge/worknaru/issues/35)에서 단일 패키지와 Daemon-first 원칙을 유지하고 Agent 관리를 Paseo에 위임했다. 위의 첫 저장 흐름은 출발 당시 범위이며, 현재 구현·명령·제약은 [개발 안내](../development.md)를 따른다.

| 코드 | 현재 책임 |
| --- | --- |
| `src/main.ts`, `application.ts`, `scripts/dev.mjs` | 독립·개발 실행과 공통 조립, 제품 전체의 시작·종료. 조립 지점이 실제 runtime 구현을 선택한다. |
| `src/paseo-*.ts`, `owned-process.ts`, `windows-runtime.ps1` | Paseo 타입·기능의 변환, 전용 구성·인증·연결과 프로세스 소유. Agent별 실행·세션·도구는 Paseo가 관리한다. |
| `src/chat-contract.ts`, `chat-runtime.ts` | 제품 공개 계약과 현재 Chat이 소비하는 작은 runtime 인터페이스. Paseo 타입을 노출하지 않는다. |
| `src/chat-daemon.ts`, `chat-service.ts`, `chat-store.ts` | 요청 검증, 동시 입력·설정·승인 판정, 대화 연결과 미확정 요청 정보. 전체 timeline과 Agent 상태 기계를 저장하지 않는다. |
| `src/chat-connection.ts`, `chat-model.ts`, `rpc.ts` | UI/headless 공통 통신, 화면 상태·초안·요청 식별자와 호출 도구. DB와 Provider를 직접 다루지 않는다. |
| `web/` | 새 Chat 표시·입력과 공통 primitive·디자인 토큰. `design-prototype/`은 기존 디자인 선택과 control 검증을 위한 예제다. |

`build:daemon`과 `test:daemon`은 Web 빌드·Vite·브라우저 없이 실행한다. `npm test`는 제품 기동·개발 실행까지, `test:web`은 브라우저까지 검사한다. 플랫폼의 제품 정책·UI·Module은 runtime 인터페이스를 통해 기능을 사용하고 vendor 의존은 연결부와 조립 지점에 둔다. 현재 실제 구현은 Paseo이며 시험용 fake가 같은 인터페이스를 사용한다. 별도 NativeRuntime이나 미래 Module용 계층은 만들지 않았다.
